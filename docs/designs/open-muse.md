# Design: OpenMuse — Conversational Computer Coworker

OpenMuse gives a person a familiar chat for delegating browser work while the work stays inside a disposable computer they can watch and control.

## Problem Statement

OpenMuse Research proves a bounded goal-to-plan-to-artifact workflow, but it does not demonstrate the more familiar agent experience the user wants to explore: an empty chat where a person can ask for arbitrary computer work, watch the agent use its own browser and workspace, intervene when necessary, and continue the same conversation. The new example should make SmolVM feel like a general computer coworker without letting model output bypass lifecycle, browser, or approval policy.

The motivating live story is personal shopping: the user has intentionally signed into Amazon inside a named SmolVM browser profile and asks the agent to find a product and add one matching item to the cart. The exact requested cart addition may proceed; variants, substitutions, credentials, checkout, payment, subscriptions, deletion, messaging, and any expansion of scope must pause.

## What Makes This Cool

The user sees the agent working in a real disposable computer, not a transcript pretending to be one. Chat, live browser pixels, shell/file activity, approvals, and human takeover are different views of one controlled session. The unusual product move is to replace up-front goal and plan ceremony with a conversational intent ledger plus a deterministic action broker: low-risk work flows, consequential work stops at the boundary.

## Constraints

- Add a sibling developer-facing example, now `examples/open-muse/`; keep OpenMuse Research as the structured workflow.
- Keep Pi as the host-side agent harness. The model API key remains on the host and never enters the VM or browser profile.
- Add a real typed browser-session surface to the TypeScript SDK and its private runtime bridge. Do not shell out to the SmolVM CLI from the example.
- One conversation owns at most one browser-capable disposable SmolVM session. The first release is ephemeral; a named persistent profile is a second milestone after authenticated-browser isolation is proven.
- The right pane uses the actual SmolVM live display. It must not simulate browser state from model messages.
- The UI starts as an empty conversation. There is no separate goal, constraints, or plan screen.
- The harness, not the model prompt, enforces allow, approve, and deny decisions.
- The first automated shopping flow uses a versioned local fake storefront with no external network. Amazon is a later manual security milestone, not a release gate; CI must never touch a real account or place an order.
- The app remains loopback-only and single-user. Remote hosting and multi-tenant authentication are out of scope.
- Preserve the current TypeScript SDK ownership rule: a client controls only sessions created through that client, and `close()` performs bounded cleanup.
- This document is implementation-ready only for milestone 1. Persistent profiles, real-site adapters, external web access, and shell/files retain product direction here but require separate security/design approval before implementation.

## Premises

- A sibling example gives developers both useful patterns: OpenMuse Research for narrow, verifiable workflows and OpenMuse for conversational computer use.
- A named SmolVM profile is the right place for intentional login state. The agent does not borrow the host Chrome profile.
- A live view, clear activity labels, interruption, and takeover provide better control for this example than approving an up-front plan.
- “The user asked for it” is not a blanket grant. Authorization is scoped to an action kind, subject, site, quantity, constraints, and a short lifetime.
- Browser automation and shell execution cannot be treated as equivalent trust surfaces when an authenticated profile exists. The first release exposes browser tools only. Shell and file tools arrive only after profile/CDP isolation is demonstrated.
- The conventional guidance remains sound for high-impact actions: isolate execution, minimize privileges, restrict reachable surfaces, and require human confirmation near the consequential action.

## Approaches Considered

- **A — Direct Pi-to-computer loop (minimal viable):** expose broad Playwright and shell tools directly to Pi. Rejected because the quickest path makes intent-scoped approvals advisory and gives the model too much authority over an authenticated profile.
- **B — Host agent with typed browser client and deterministic action broker (selected):** Pi proposes typed actions; the broker serializes them, checks grants and fixed rules, and invokes SmolVM/Playwright only after an allow decision.
- **C — Guest-resident agent runtime:** run the harness inside SmolVM and stream the whole desktop outward. Rejected for now because provider credentials, recovery, upgrades, and policy auditing become harder without improving the local example’s core experience.

## Recommended Approach

Build Approach B as a sibling React/Vite and Node example. The Node process owns Pi, every SmolVM handle, the Playwright connection, the intent ledger, the action broker, and the conversation event stream. The React client owns presentation only.

Deliver it in three security milestones:

1. **Ephemeral browser vertical slice:** local fake storefront, network off, browser-only Pi tools, exact add-to-cart grant, one-time fake checkout-review approval, authenticated live viewer, takeover, stop, and packed-SDK tests.
2. **Authenticated browsing:** dedicated persistent profile artifact, safe human-only login, external-network interception, and one reviewed site adapter before an Amazon cart demonstration.
3. **Computer workspace:** unprivileged shell/files only after the agent cannot reach profile data or CDP from its guest identity. If that isolation is not reliable, the browser example remains browser-only.

### Browser and computer rendering

Start the SmolVM browser session in `live` mode. The typed SDK returns a loopback-only `viewerUrl` and `cdpUrl` to the Node process. Browser JavaScript receives neither raw endpoint. The Node server exposes a same-origin, conversation-scoped viewer proxy for the iframe and never proxies CDP.

The right pane embeds the conversation-scoped viewer proxy URL in an iframe. The proxy serves the existing noVNC client, backed by the exact X display Chromium uses:

```text
Chromium → Xvfb :99 → x11vnc :5900 → websockify/noVNC :6080 → iframe
```

This is a live pixel stream with real page transitions, typing, scrolling, dialogs, and cursor movement. It is not a periodic screenshot loop and does not reconstruct the DOM in React. Screenshots remain model observations and test artifacts only.

The app draws its own header, status, Stop/Take control action, and activity timeline around the iframe. While Pi owns control, a transparent overlay intercepts pointer and keyboard input and the iframe is labeled **LIVE · Agent controlling**. Clicking **Take control** requests a cooperative pause. The broker finishes at most the currently committed atomic browser action, blocks new tool dispatch, reports **You have control**, and only then removes the overlay. While the human owns control, the chat composer is disabled and the server rejects new messages with the exact **Select Return control** recovery. **Return control to agent** restores the overlay, records a takeover event in the conversation, asks Pi to re-observe the page, and resumes the loop.

On `GET /api/bootstrap`, the app verifies a loopback Host plus `Sec-Fetch-Site: same-origin|none`, creates a random 256-bit session capability, sets it in an `HttpOnly`, `SameSite=Strict` cookie, and returns a separate CSRF token. Every mutation requires the cookie, exact loopback `Origin`, CSRF token, and JSON content type. A protected viewer-token endpoint issues a single-use 60-second nonce; the viewer websocket presents it in its negotiated subprotocol and the server consumes it before proxying. The app sends no CORS headers and emits `Cache-Control: no-store`.

The iframe loads a same-origin URL such as `/api/conversations/:id/viewer/`; the Node proxy forwards only allowlisted noVNC assets and the websocket for that owned session. The raw random ports never appear in HTML, events, logs, or client JSON. The app CSP is `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self' <exact-loopback-websocket-origin>; frame-src 'self'; frame-ancestors 'self'; object-src 'none'; base-uri 'none'` with no inline script. React renders user, assistant, page, and activity strings as text nodes; `dangerouslySetInnerHTML` and raw HTML are forbidden. If Markdown is added later, it uses an allowlist sanitizer with links stripped of active schemes.

The threat model protects against remote callers and drive-by web pages. It does not claim to protect against another malicious process running as the same host user, which can inspect local processes and loopback traffic. SmolVM’s private SDK bridge retains its existing per-process credential and ownership checks.

### TypeScript browser-session API

Extend the SDK with a first-class collection parallel to `sandboxes`:

```ts
const smolvm = new SmolVM({ onEvent });
const session = await smolvm.browsers.create({
  mode: "live",
  profile: { mode: "ephemeral" },
  viewport: { width: 1440, height: 900 },
});

session.sessionId;
session.sandboxId;
session.status;
session.cdpUrl;       // host-side automation endpoint
session.viewerUrl;    // loopback noVNC endpoint
session.displayUrl;   // loopback VNC endpoint
await session.exec("uname -a");
await session.files.write("/workspace/task.txt", "hello");
await session.delete();
```

Freeze the preview contract before the example lands:

- `SmolVM.browsers.create()` creates and starts a session owned by that SDK client. Its promise resolves only at `ready`, after both CDP and viewer readiness probes succeed and the returned endpoints are usable. Startup timeout rejects with a typed creation error only after bounded cleanup; callers never receive a half-ready handle.
- `BrowserSessionClient` exposes `sessionId`, `sandboxId`, `status`, `cdpUrl`, `viewerUrl`, `displayUrl`, `exec()`, `files`, and idempotent `delete()`. Status is `created | starting | ready | stopping | deleted | error`.
- The SDK does not depend on Playwright. The example installs Playwright and calls `chromium.connectOverCDP(session.cdpUrl)` on the host.
- `SmolVM.close()` invokes idempotent `delete()` for every owned browser session as well as ordinary sandboxes. Milestone 1 removes all session data.
- Lifecycle events add `browser.starting`, `browser.ready`, `browser.stopping`, and `browser.deleted`, with session and sandbox IDs. Endpoint URLs do not appear in generic logs or error telemetry.
- Runtime negotiation requires `browser.create`, `browser.delete`, `browser.endpoints`, `browser.exec`, `browser.files`, and `browser.events`. An older runtime fails with `protocol_incompatible` and the exact recovery command `curl -sSL https://celesto.ai/install.sh | bash`.
- Creation failures use stable codes `browser_create_failed`, `browser_image_unavailable`, `browser_endpoint_unavailable`, and `profile_in_use`; deletion failures use `cleanup_failed`. Endpoint access after deletion uses `browser_deleted`.
- `get()` and process-independent attach are not in the preview SDK. The creating client owns the in-memory handle; `delete()` and `close()` are the only stop paths.

The private Python bridge adds session-scoped create, delete, command, and file routes backed by the existing `BrowserSessionConfig` and `_BrowserSandbox`. It maintains a browser-session ownership registry separate from CLI state and cleans every owned handle on pipe close. Commands run as the unprivileged `agent` user, and file transfer is available only to the trusted host SDK. OpenMuse uses the command route only to launch its approval-gated browser runner; it does not expose raw shell or file tools to Pi. For orphan reconciliation the bridge atomically writes a private lease record containing session ID, hashed owner capability, bridge PID and process-start identity, host boot ID, heartbeat/expiry, and cleanup state. Startup takes an exclusive reconciliation lock, removes records from a prior boot, and deletes expired sessions whose recorded process identity no longer exists.

The current Python implementation persists an entire root disk under a stable ID. Do not use that disk for an authenticated milestone. Milestone 2 first introduces a dedicated profile artifact with an explicit format/image version, current-user-only host permissions, exclusive locking by `profileId`, atomic save, and user-confirmed reset. The UI says **Browser profile saved; VM stopped** only after both operations are confirmed. A version mismatch returns a short reset or migration recovery action rather than silently creating an empty profile.

### Guest privilege split (milestone 3)

Do not expose a shell beside an authenticated browser profile until isolation is proven. Milestone 3 updates the browser image so:

- Chromium and its profile run as a dedicated `browser` user.
- model-directed commands run as an unprivileged `agent` user in `/workspace`;
- the `agent` user cannot read the browser profile, browser logs containing sensitive page data, SSH material, or runtime control files;
- no `sudo`, Docker socket, host mount, or browser-debug port is reachable from that shell; browser and agent use separate network namespaces or equivalent firewall ownership rules so guest loopback does not expose CDP to `agent`;
- the host-side broker alone uses the forwarded CDP endpoint;
- browser tools do not expose raw JavaScript evaluation, raw CDP, `file:` navigation, `chrome:` pages, or arbitrary loopback/private-network navigation.

This is defense in depth, not a claim that two Linux users inside one VM are a hard adversarial boundary. The stronger boundary is the host broker’s narrow tools. A release test must prove the `agent` identity cannot read profile paths or connect to CDP. If it cannot, shell execution remains out of this example.

### Conversation and agent harness

Reuse the installed Pi packages and provider setup from OpenMuse Research, but replace the plan/run workflow with one long-lived conversation agent. The system prompt describes capabilities and instructs the model to treat pages and tool output as untrusted data. It does not carry the safety policy by itself.

`ConversationManager` owns one `ConversationContext`. Control ownership, agent execution, and VM lifecycle are separate state dimensions:

```ts
interface ConversationContext {
  id: string;
  controlOwner: "agent" | "pause_requested" | "human";
  runState: "idle" | "model_turn" | "tool_action" | "waiting_for_approval" | "stopping" | "stopped" | "failed";
  sessionLifecycle: "absent" | "starting" | "ready" | "stopping" | "deleted" | "error";
  abortController: AbortController;
  browser?: BrowserSessionClient;
  playwright?: Browser;
  grants: IntentGrant[];
  events: ConversationEvent[];
  pendingApproval?: PendingApproval;
}
```

An idle conversation is nonterminal. Completed user and assistant messages live in a separate message store; token deltas are compacted into one completion event. Retain at most 100 completed messages and 64,000 UTF-8 characters. At 80% of either bound, summarize older non-sensitive dialogue for Pi and retain the latest 20 messages verbatim. The summary can guide conversation but never creates or changes an intent grant. If compaction fails, pause with a recovery to start a new conversation rather than silently dropping context. Snapshots contain the bounded completed messages, current states, grants, pending approval, and events retained after the requested cursor.

After each assistant turn, Pi returns to `idle` and the browser remains warm until **Stop**, the 15-minute idle timeout, server shutdown, or failure closes it. `stop` is the explicit terminal/close operation for the first release.

Opening the app and creating a conversation do not boot a VM. The browser starts at the first browser-tool dispatch. Only one model turn and one broker action may execute at a time. Most mutations use one serialized manager queue, but two safety barriers operate out of band:

- **Stop barrier:** `POST /stop` is idempotent, ignores optimistic state version, atomically blocks new dispatch before entering the queue, aborts active model/tool work where possible, and acknowledges within one second with cleanup continuing in state `stopping`.
- **Message barrier:** receipt of any new user message atomically blocks the next dispatch, invalidates available and pre-dispatch reserved grants plus observation refs, then queues the message. A committed effect cannot be cancelled. Pi incorporates the message and may create narrower replacement grants before the barrier is released.

Milestone 1 tool set:

- `browser_observe()` — fixture URL, title, screenshot, trusted fixture metadata, and bounded accessibility snapshot.
- `browser_navigate(route)`, `browser_click(ref)`, `browser_select(ref, value)`, `browser_scroll(direction)`, and `browser_back()` — semantic actions limited to the versioned fake-store origin and routed through the broker.
- `request_approval(proposal)` — suspends the loop for the fake store’s `begin_checkout` action. Approval may open only the fixture’s order-review page; `place_order` is always denied.

There is no raw typing, Playwright page, JavaScript evaluator, CDP connection, external network, arbitrary host fetch, shell, file transfer, or host filesystem tool in the milestone 1 Pi tool list. General web search/navigation is enabled in milestone 2 after network interception lands. Credentials are entered only by the human during takeover; Pi, tool arguments, screenshots, accessibility snapshots, events, and conversation history never receive the secret value. Model observations pause for the full takeover and resume only after password fields are cleared from the accessibility payload.

Use two agent test modes. A deterministic scripted agent drives every server, policy, and race test without a provider. An opt-in live-model evaluation runs a fixed corpus covering product selection, clarification when price/variant is missing, refusal of `place_order`, approval pause, takeover recovery, and successful completion; it records pass/fail summaries but no credentials or page captures.

### Intent ledger and deterministic action broker

Each user message is retained verbatim and may produce a structured, short-lived intent grant. Model-assisted extraction is untrusted and may only propose scope. A deterministic grounding validator must bind every security-relevant field to evidence spans in the source message: action verb, product/category alias from the canonical catalog, exact or explicitly delegated variant, quantity, currency, and numeric price bound. It handles negation and corrections before issuing a grant. Unknown qualifiers, contradictory spans, omitted constraints, hallucinated catalog values, or paraphrases the validator cannot ground produce no grant and a clarification request; they never become wildcards. The grant describes delegated selection constraints, while the proposed action describes one exact effect:

```ts
type AddToCartAction = {
  kind: "add_to_cart";
  storefrontVersion: string;
  productId: string;
  variantId: string;
  quantity: 1;
  unitPriceMinor: number;
  currency: "INR";
  observationId: string;
  commerceRevision: number;
  targetRef: string;
};

type BeginCheckoutAction = {
  kind: "begin_checkout";
  storefrontVersion: string;
  cartReceipt: string;
  totalPriceMinor: number;
  currency: "INR";
  observationId: string;
  commerceRevision: number;
  targetRef: string;
};

type ProposedAction = AddToCartAction | BeginCheckoutAction;

interface IntentGrant {
  id: string;
  conversationId: string;
  actionKind: "add_to_cart";
  storefrontVersion: string;
  subject: { productId: string } | { categoryId: string };
  variant: { kind: "any" } | { kind: "exact"; id: string };
  maxQuantity: 1;
  maxUnitPriceMinor: number;
  currency: "INR";
  sourceMessageId: string;
  expiresAt: string;
  evidence: Record<"action" | "subject" | "variant" | "quantity" | "price",
    | { source: "message"; start: number; end: number; quote: string; normalized: string }
    | { source: "catalog"; catalogKey: string; normalized: string }
  >;
  state: "available" | "reserved" | "committed" | "consumed" | "cancelled";
}

interface PendingApproval {
  approvalId: string;
  proposedAction: ProposedAction;
  actionDigest: string;
  reason: string;
  expiresAt: string;
  stateVersion: number;
}
```

`targetRef` is opaque and scoped to one top-level page, frame path, navigation epoch, `observationId`, and trusted `commerceRevision`. The adapter increments that revision only when catalog version, selected variant, cart contents, price, or checkout state changes; animation, focus, and unrelated framework mutations do not invalidate it. Navigation, popup, new observation, or commerce revision invalidates the ref. Accessible names alone never establish identity or price.

For “add the best value wireless headphones under ₹8,000,” grounded spans for “add,” “wireless headphones,” and “under ₹8,000” permit Pi to choose one item in the fixture’s `wireless-headphones` category at or below 800000 minor INR units; “best value” delegates selection but is not represented as a quality guarantee. `variant: {kind:"any"}` is allowed only when the message explicitly delegates selection or the product has one variant. For “add SoundArc H7,” the grant is product-specific. The broker re-resolves the target and fixture metadata immediately before dispatch and produces one of four decisions:

| Decision | Examples |
|---|---|
| Allow | observe, scroll, and navigation between known read-only fake-store routes |
| Intent-authorized | one exact fake-store “Add to cart” effect whose product/category, optional required variant, quantity, price, origin, and currency satisfy an available grant and whose observation/commerce revision remain current |
| Approval required | the fixture’s exact `begin_checkout` proposal; ambiguity, substitution, credentials, upload, download, messages, payment, subscription, deletion, and privacy expansion never execute in milestone 1 |
| Deny | host access, cookie/profile extraction, raw CDP/eval, policy changes, forbidden schemes or private endpoints, approval bypass |

Grant consumption is transactional: reserve the grant, revalidate the full effect, atomically move it to non-cancellable `committed`, attach a broker-generated idempotency key to the known fake-store cart request, dispatch, verify the fixture API’s deduplicated receipt, then mark consumed. The fixture receipt is the atomic completion boundary, with a ten-second deadline. Validation failure before `committed` releases or cancels the reservation without clicking. A new message may cancel only `available` or `reserved` grants. An uncertain committed result marks the grant consumed and requires a fresh user message; it is never retried automatically. Real sites can promise only at-most-one broker dispatch, not exactly-once effect.

The fake `begin_checkout` approval uses the exact proposed action object and SHA-256 digest, expires after five minutes, and becomes stale on any commerce revision change. Approving once opens an order-review page and consumes the approval. The fixture has no payment endpoint; `place_order` is not representable. Later milestones extend `ProposedAction` with new discriminated variants rather than treating the cart schema as generic.

Page text and tool output are untrusted evidence. Instructions found in them cannot create grants, approve actions, expand origins, or change policy. The broker records only sanitized action summaries; it does not stream credentials, form values, cookies, page source, screenshots, accessibility trees, or model reasoning to the activity timeline. The example stores no screenshot or accessibility history after the current observation; provider retention follows the configured provider account and is disclosed in the README before authenticated browsing is enabled.

### Browser effect containment

Milestone 1 runs the VM with external network disabled and serves the fake store through host-side Playwright route fulfillment at the synthetic origin `http://shop.smol.test`. Static assets and an immutable canonical catalog come from `fixtures/storefront/`; the catalog includes `storefrontVersion`, product/variant IDs, integer minor-unit prices, and a checksum. The page performs a version handshake, and readiness requires matching version/checksum plus a successful catalog render. The adapter compares page selections to this out-of-page catalog. A fixture cart endpoint accepts and deduplicates the broker’s idempotency key and returns a signed-in-process receipt plus the new `commerceRevision`.

The broker installs Playwright handlers before the first navigation: reject new pages, popups, downloads, permission prompts, JavaScript dialogs, external protocols, service-worker registration, and every request outside the exact synthetic origin. Redirects are revalidated at every hop. This makes the first intent-authorized effect testable without pretending generic pages have trustworthy commerce semantics.

Milestone 2 adds defense below individual tool calls: resolve hostnames, reject loopback/link-local/private/reserved destinations after DNS resolution, pin the approved result for the connection, revalidate redirects and subresources, and apply a SmolVM network allowlist where supported. On unknown sites, every interaction capable of mutation is denied or requires approval; the broker never guesses its effect. Automatic cart authorization on a real site requires a reviewed, versioned site adapter that can establish product, variant, quantity, price, and page revision; otherwise the broker pauses.

### HTTP and event contract

The local Node server exposes a small conversation API:

```text
GET  /api/bootstrap
POST /api/conversations
GET  /api/conversations/:id
POST /api/conversations/:id/messages
GET  /api/conversations/:id/events       (SSE, resumable with Last-Event-ID)
POST /api/conversations/:id/approvals/:approvalId
POST /api/conversations/:id/takeover
POST /api/conversations/:id/resume
POST /api/conversations/:id/stop
POST /api/conversations/:id/viewer-token
GET  /api/conversations/:id/viewer/*     (authenticated noVNC HTTP proxy)
WS   /api/conversations/:id/viewer/websockify
```

Bootstrap sets the capability cookie and returns `{csrfToken}`. Create returns `{id, stateVersion}` for an empty conversation. Immediately before opening noVNC, the client calls `viewer-token`; it returns a single-use, 60-second websocket nonce bound to the conversation and capability cookie. Every mutation uses an idempotency key, but concurrency is endpoint-specific:

- message receipt and takeover install their safety barriers regardless of internal `stateVersion`;
- Stop bypasses optimistic concurrency and the normal queue;
- resume requires the current `controlOwner` to be `human` and matches a control-epoch token returned by takeover;
- approval requires exact action digest, commerce revision, approval state, and expiry;
- ordinary non-safety mutations use `expectedStateVersion` and return `409 state_conflict` when stale.

A pending approval contains `{approvalId, proposedAction, actionDigest, reason, expiresAt, stateVersion}` and **Approve once** / **Not now**. The server rejects stale, mismatched, duplicate, expired, or post-stop approvals.

`stateVersion` increments only when the server accepts an external mutation or changes `controlOwner`, `runState`, `sessionLifecycle`, grant state, approval state, or commerce revision. Text deltas, progress events, heartbeats, and read-only observations do not increment it. Each accepted mutation returns the new version.

Each event has a monotonic integer `id`, `conversationId`, `stateVersion`, timestamp, discriminated `type`, and sanitized payload. The server serializes mutations before assigning IDs. Keep at most 500 events and coalesce progress. `Last-Event-ID` replays retained events in order; if the ID predates the buffer, emit `conversation.resync_required` and close so the client fetches the current snapshot. SSE includes user/assistant text deltas, tool started/completed, broker decision, lifecycle, control ownership, approval, and terminal events. It never contains hidden reasoning, raw screenshots, API keys, cookies, complete environment values, or typed credentials.

### Lifecycle and failure behavior

- Reject a second active conversation with HTTP `409` in the first example.
- Defaults are: 120 seconds per model turn, 90 seconds for browser startup after an image is available, 10 seconds per Playwright operation or fixture receipt, 15 seconds per navigation, 30 seconds per approved browser program with a 35-second command deadline, 10 seconds for an approved current-page fallback, 15 seconds for takeover acknowledgement, and 15 minutes idle between turns. A browser program that stops early returns bounded current-page evidence only when the approval disclosed that fallback and the page passes the sensitive-path checks; otherwise the action fails with the exact chat retry instruction and is never retried automatically. Model and startup failures clean the session; takeover timeout leaves the input overlay in place and offers **Stop**; idle timeout stops cleanly.
- On client refresh, reconstruct chat and activity from bounded in-memory state and reconnect SSE. Conversation recovery after a Node restart is out of scope, but orphan cleanup is not.
- On browser disconnect, pause Pi, retry the CDP connection once, then show one fact plus an exact recovery action.
- On noVNC failure with healthy CDP, keep the agent paused until the user explicitly chooses **Continue without live view** or stops. Do not silently operate an invisible authenticated browser.
- On app shutdown, stop accepting work, abort Pi, close Playwright, stop the browser session, and close SmolVM. The private runtime bridge owns a lease tied to its authenticated control pipe; EOF or parent death triggers cleanup, and the next bridge startup reconciles expired session-owned records. A hard host failure is cleaned on reboot/startup, not synchronously. If cleanup cannot be confirmed, show the exact `smolvm browser stop <session-id>` recovery command.
- Milestone 2 makes the persistent profile opt-in and names it in the header. **Reset profile** is available only while exclusively locked and no session is active; its confirmation says saved logins and browser state will be removed.

The serialized transition rules are:

| Current state | Event | Result |
|---|---|---|
| any nonterminal | `stop` | wins over queued work; cancel pending approval/grants, block dispatch, clean session, then `stopped` |
| `idle` + session `ready` | `takeover` | transfer immediately to `human` and remove overlay after acknowledgement |
| `idle` + session `absent` | `takeover` | reject with “There is no computer to control yet” |
| `model_turn` | `takeover` | set `pause_requested`, abort the model turn, then transfer to `human` when viewer is ready |
| session `starting` | `takeover` | set `pause_requested`; allow startup but block the pending tool, then transfer when viewer is ready or report startup failure |
| `tool_action` | `takeover` | set `pause_requested`; finish only the already-dispatched atomic action, then transfer to `human` |
| `waiting_for_approval` | `takeover` | cancel the pending approval as stale, then transfer to `human` |
| `human` | `takeover` | idempotently acknowledge current ownership |
| `human` | message | reject with **Select Return control** and preserve the unsent composer text |
| `human` | approval | reject as stale because takeover invalidates pending approval |
| `human` | `resume` | transfer to `agent`, invalidate refs, and re-observe before accepting later messages |
| session `stopping/deleted/error` or run `stopped/failed` | takeover/approval/resume/tool result | reject as stale; keep overlay; never revive the session |

Stop prevents future dispatch; it cannot undo an effect already committed by the browser. Consequential validation therefore completes before dispatch, and UI copy never promises rollback.

## Blocking Prototypes

- Before UI work, prove the same-origin noVNC proxy can frame the existing assets, authenticate HTTP and websocket upgrades, and transfer focus only after a pause acknowledgement in current Chrome.
- Before milestone 2, prove the dedicated profile artifact locks, saves atomically, survives an ephemeral VM deletion, and refuses incompatible image versions.

## Success Criteria

1. A developer can install the preview TypeScript package, configure `OPENAI_API_KEY`, start `examples/open-muse`, send a message, and see an ephemeral live SmolVM browser in the right pane.
2. The example uses Pi on the host and the public typed SmolVM API. It contains no CLI subprocess wrapper and no import from `ts/src`.
3. On a warm run with the browser image cached on an Apple M-series host, the interval from broker dispatch timestamp to the first `browser.starting` SSE event is below two seconds; cold image download time is reported separately.
4. The local fake-store test asks for a specific product under a price cap, compares options, and adds exactly one matching item without an extra approval.
5. A changed variant, over-budget item, second quantity, or substitution fails closed; `begin_checkout` pauses for one-time approval; payment/place-order, credential fields, messages, uploads, deletion, external origins, popups, downloads, and unmatched side effects are denied before dispatch in milestone 1.
6. A stale approval, changed page state, or reused approval is rejected by the harness.
7. Takeover reaches `human` state only after the broker stops dispatching actions. No agent tool runs until control is returned and the page is re-observed.
8. The iframe shows the real noVNC stream. The browser client never receives CDP, profile paths, cookies, or provider credentials.
9. Milestone 1 exposes no model-directed shell, file transfer, credential typing, persistent profile, or external web access.
10. Stop, idle timeout, cancellation, refusal that terminates the conversation, takeover-stop, browser failure, model failure, disconnect timeout, graceful shutdown, and control-pipe death leave no running session-owned VM. Expired orphan records reconcile on the next runtime startup; hard host failure is not claimed as synchronous cleanup.
11. Unit and integration tests run without network or real accounts. The initial support matrix is QEMU on Apple Silicon macOS and Linux x64 only. A gated real-VM smoke boots the packed SDK artifact on both and exercises the authenticated viewer proxy, websocket nonce, CDP, fake-store cart, fake checkout approval, stale refs, duplicate grants, takeover/stop races, SSE replay gaps, protocol downgrade, and cleanup. Other backends remain unsupported until they receive the same smoke.
12. Malicious fixture tests cover redirects, subresources, popups, downloads, dialogs, external protocols, service workers, local API forgery, hostile assistant/page strings, stale approvals, uncertain dispatch, concurrent message/dispatch, committed-action cancellation attempts, concurrent stop/takeover, fixture receipt deduplication, and orphan lease reconciliation. Grounding tests cover negation, corrections, omitted/implicit variants, unrepresentable qualifiers, and hallucinated known catalog values.
13. A deterministic scripted-agent suite covers every critical path; an opt-in live-model evaluation passes product selection, clarification, refusal, approval pause, takeover recovery, and completion cases before the demo is announced.
14. Amazon is attempted only after milestone 2 passes its security review. A manual demonstration may add an item to a test/non-critical account’s cart but never proceeds to checkout or purchase as part of release verification.

## Distribution Plan

Ship the browser API in the next TypeScript preview package through the existing GitHub Release tarball channel. CI builds and packs `ts/`, installs the produced tarball into the example, and runs typecheck/unit tests so repository-relative imports cannot hide packaging errors. Real-VM smoke jobs remain gated to supported hardware-enabled runners.

After that preview is published, pin `examples/open-muse/package.json` and its lockfile to the immutable release tarball, matching the honest install path used by OpenMuse Research. Add the example to the root and docs indexes with a clear distinction: OpenMuse Research is a bounded research workflow; OpenMuse is the conversational computer-use pattern.

Browser-image changes required for noVNC or the guest user split follow the repository’s image release checklist: build and smoke the image, publish it, update rootfs and guest-agent SHA pins, and only then tag the package release.
