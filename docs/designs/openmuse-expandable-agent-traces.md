# Design: Expandable OpenMuse Agent Traces

Generated by /office-hours on 2026-09-15
Branch: main
Repo: CelestoAI/SmolVM
Status: APPROVED
Mode: Builder

## Problem Statement

OpenMuse currently shows a separate **Live activity** panel containing short sanitized labels such as “Browser tool started.” Those labels establish that work is happening but do not help a curious user understand what the agent observed, which tool it called, what came back, or why a run failed.

Replace that panel with a ChatGPT-like trace disclosure attached to each assistant turn. It stays collapsed during ordinary use and expands into the chronological, agent-visible details of the run.

## What Makes This Cool

The browser remains visible, but the user can also inspect the agent’s actual working record. A completed answer can say **Worked for 8s · 4 steps**; expanding it reveals the observation, extraction, tool inputs, tool results, approvals, errors, and timings that produced that answer.

Ordinary user and page data appears verbatim. This is not a generic sanitized activity summary. Credential-class data remains outside the trace entirely.

Wireframe: `~/.gstack/projects/CelestoAI-SmolVM/designs/openmuse-expandable-traces/sketch.png`

## Constraints

- Show the exact traceable payload that crossed the agent/tool boundary, except documented credential omission and size truncation. Do not generate a second LLM explanation of it.
- Do not expose hidden chain-of-thought. The product can show tool activity and explicit model-visible observations, but it must not claim to reveal private model reasoning that the provider does not return.
- Passwords, cookies, authorization headers, payment fields, API tokens, one-time codes, and takeover-only input must never enter the trace buffer.
- Keep raw traces out of durable conversation checkpoints and the existing sanitized `ConversationEvent` contract.
- Trace endpoints remain authenticated and loopback-only under the existing OpenMuse session capability.
- Bound memory and payload size so a large page or long run cannot exhaust the Node process or freeze the client.
- Existing unrelated changes in `open-muse/.env.example`, `open-muse/eval/run-live.ts`, and `open-muse/server/index.ts` belong to another workstream and must be preserved.

## Premises

1. The trace is a user-facing inspection surface, not a server log or developer console.
2. “Raw” means verbatim data the agent was allowed to see. It does not mean browser state the agent was forbidden to access.
3. A trace is session-scoped debugging context. The chat checkpoint may survive a restart; the raw trace does not.
4. The trace belongs to one product turn: an accepted user message plus every model/tool continuation it causes, including approval resume and recovery. Queue serialization alone is not an ownership boundary, so ownership travels through an explicit execution record.
5. The current sanitized activity events remain useful for durable recovery and diagnostics, but no longer need a dedicated UI panel.
6. OpenMuse's existing loopback session model trusts other processes running as the same local user. Raw traces do not claim stronger process isolation than the rest of the local app.

## Approaches Considered

### Approach A: Enrich the existing activity events

Add raw arguments and results to `ConversationEvent` and render those events as expandable rows. This is the smallest diff, but it mixes raw page data into durable checkpoints and turns a stable recovery contract into a debugging payload.

### Approach B: Separate ephemeral trace stream

Maintain an in-memory trace buffer distinct from `ConversationContext.events`. Publish it through a separate authenticated stream, group records by model turn, and render one collapsed disclosure per turn. This is the selected approach because trace data has a different lifetime, size, and security contract from durable events.

### Approach C: Capture only while expanded

Start detailed capture only after the user opens the disclosure. This reduces retained data but misses the steps that caused the user to become curious, especially failures and fast tool calls.

## Recommended Approach

### Interaction

- While a turn is running, render a collapsed row after the user message: **Working · 3 steps · 6s**.
- While the run waits for approval, use **Waiting for approval · 3 steps · 6s active**. Human decision time does not increase the active-work timer.
- Update the step count and elapsed time without opening the disclosure automatically.
- Keep one stable, keyed trace container between the user message and the assistant response. When the response completes, change its label to **Worked for 8s · 4 steps** without moving the container in the DOM.
- Expanding the turn shows chronological step summaries.
- Each step is independently expandable. Its detail view uses a monospace block for the exact structured input or output.
- A failed parent trace remains collapsed by default but uses the label **Stopped after 6s · failed at step 3**. If the parent is already open, expand the failed child without moving keyboard focus.
- Remove the standalone **Live activity** panel. The computer view remains unchanged.
- Preserve traces when the user collapses or expands the computer pane; clear them only with the conversation session.

### Terminology

- **Turn:** one accepted user message and the serialized model/tool work it starts. `ConversationManager.turnQueue` already prevents two turns from executing concurrently.
- **Trace step:** one user-recognizable action such as observing a page, extracting content, requesting approval, or using a browser control. A tool’s input, output, timing, and failure are one step, not separate counted rows.
- **Trace event:** one append or replacement delivered to clients. Events have their own cursor; a step can be replaced many times while keeping a stable step ID.
- **Traceable payload:** data already allowed across the model/tool boundary. It excludes takeover-only input and structurally protected credential sources, and it may be size-truncated.
- **Session:** the lifetime of the in-memory `ConversationManager` process. A browser refresh stays in the same session; a server restart does not.

### Trace model

Add an in-memory `TraceBuffer` owned by `ConversationManager`, not by the serialized `ConversationContext`. Never infer ownership from a manager-global "current turn":

```ts
type TraceStepKind = "tool" | "browser_observation" | "approval" | "system";

type TraceStepState = "started" | "completed" | "failed" | "cancelled";

interface TracePayload {
  value?: unknown;
  truncated?: true;
  omittedReason?: "credential" | "takeover-only" | "not-model-visible";
}

interface TraceStep {
  id: number;
  conversationId: string;
  turnId: string;
  sequence: number;
  kind: TraceStepKind;
  state: TraceStepState;
  label: string;
  startedAt: string;
  completedAt?: string;
  durationMs?: number;
  input?: TracePayload;
  output?: TracePayload;
  revision: number;
}

type TraceEvent =
  | { eventId: number; operation: "step_upsert"; conversationId: string; turnId: string; step: TraceStep }
  | { eventId: number; operation: "turn_upsert"; conversationId: string; turn: TraceTurn }
  | { eventId: number; operation: "turn_evict"; conversationId: string; turnId: string }
  | { eventId: number; operation: "turn_completed"; conversationId: string; turnId: string; state: "completed" | "failed" | "cancelled"; completedAt: string };

interface TurnExecution {
  turnId: string;
  conversationId: string;
  userMessageId: string;
  state: "queued" | "running" | "waiting_for_approval" | "completed" | "failed" | "cancelled";
  acceptedAt: string;
  activeStartedAt?: string;
  accumulatedActiveMs: number;
  terminalAt?: string;
  revision: number;
}

type TraceTurn = Pick<TurnExecution, "turnId" | "conversationId" | "userMessageId" | "state" | "acceptedAt" | "activeStartedAt" | "accumulatedActiveMs" | "terminalAt" | "revision">;
```

Generate `TurnExecution` when `ConversationManager.send()` accepts a user message. Pass it explicitly into every queued `runTurn` closure, broker instance/callback, trace capture call, and assistant completion. Copy `turnId` into `PendingApproval` and recovery metadata so `approve()` and `continueInterrupted()` resume the same product turn even though they invoke `agent.prompt()` again. Attach it to the eventual assistant message and every trace step. Existing checkpoint migrations treat missing message `turnId` values as legacy messages with no trace.

Because the SDK agent and its broker are reused, wrap each `agent.prompt()` in Node `AsyncLocalStorage<TraceScope>` and make the broker's trace adapter read only that async-scoped execution and current step. Approval resolution receives its execution directly from `PendingApproval`; recovery receives it from recovery metadata. Do not use a manager-global current turn. `runTurn()` checks `isCurrentExecution(execution)` before its first mutation, and repeats the fence after every awaited model, browser, approval, persistence, and startup call before mutating conversation state, messages, or the active trace. A stale continuation may only terminalize its own already-cancelled trace record.

If a new user message aborts an older execution, terminalize the older turn as `cancelled` before accepting the replacement. Approval decline or expiry terminalizes its approval step and product turn as `cancelled`. A second accepted message always receives a new execution record; no mutable manager-global turn ID is reused.

Trace step IDs and trace event IDs are separate monotonically increasing sequences within the live conversation. A started step keeps its step ID and increments `revision` when it completes, fails, or is cancelled. Completion or failure updates that same row; there are no separate result/error rows. Each replacement receives a new `eventId`; `Last-Event-ID` and snapshot cursors refer only to event IDs. Clients accept a replacement only when its revision is newer than the stored step.

| Transition | Trace mutation |
| --- | --- |
| Tool starts | Insert one `started` step at revision 1. |
| Tool returns | Replace that step as `completed`, attach output and duration, increment revision. |
| Tool throws | Replace that step as `failed`, attach safe error and duration, increment revision. |
| Stop, takeover, supersession, or shutdown | Mark every started step and the turn `cancelled` with terminal timestamps. |
| Approval requested | Complete the tool step with its model-visible `approvalRequired` result; add a `started` approval step and pause active time. |
| Approval approved | Complete the approval step, resume active time, and add a new tool step for approved execution. |
| Approval declined or expired | Complete/cancel the approval step and cancel the product turn. |
| Recovery required | Fail the current step and retain `turnId` in recovery metadata; Continue resumes turn-level model state and later tools add normal steps to the same turn. |

Turn state changes increment `TraceTurn.revision` and publish `turn_upsert`. The snapshot returns `{ cursor, turns: TraceTurnWithSteps[], limits }`. The client replaces a turn or step only when the incoming revision is newer. This carries approval-paused timing without one-second server events.

### Capture points

- `agent.started` updates the turn state without creating a visible step or exposing provider-private reasoning.
- A shared `withToolTrace()` wrapper around every production `AgentTool.execute` owns start, completion, validation-failure, and thrown-error transitions. It records only a trace-safe projection, never the raw model-supplied argument object.
- Browser observation/extraction records the exact bounded payload returned to the model.
- Tool completion records the exact structured result returned to the model.
- Approval records the proposal shown to the user and the user’s approve/decline decision, excluding hidden action material.
- Errors record the model-visible or user-visible error plus a stable safe error code. Raw stack traces remain server logs, not user traces.
- Assistant completion terminalizes the turn and records final active duration; the assistant message itself remains the source of the final answer text.

Capture only through `toTraceableToolInput(operation, resolvedTarget, guestSafetyResult)`. This projection returns a new JSON-safe value and is the only tool-input type accepted by `TraceBuffer`; the original operation object must never be passed to trace code. Invalid parameters create a failed step with the tool name and safe validation error but no raw input. The separate HTTP approval path passes an explicit trace transaction into `resolveApproval()` so approved execution gets its own step even though it does not pass through `AgentTool.execute`. Do not reconstruct “raw” data later from sanitized lifecycle events.

Every recorder method is synchronous and no-throw. It commits the canonical mutation before fan-out, catches each subscriber independently, and ejects only the failing subscriber. A normalization, accounting, or canonical-buffer failure attempts one bounded **Run details unavailable** sentinel, disables capture for that turn, and never changes the tool result or agent state.

### Credential exclusion and threat model

Apply structural exclusion before insertion into `TraceBuffer`:

- Never trace cookies, storage, request headers, environment variables, browser profile data, or clipboard data because none of those sources may cross the agent boundary.
- For fill operations, trace the field ref and metadata but omit the value when the target is password, payment, authentication-code, token, or other sensitive input.
- For every `fill`, the started trace revision contains only the ref and safe target metadata. The approved guest program revalidates the page marker, resolves the target, classifies `type`/`autocomplete`, and performs `fill()` in one execution immediately before returning a structured `{ outcome, fieldClass }` result that never contains the submitted value. Only `{ outcome: "filled", fieldClass: "ordinary" }` allows the broker to attach its held value to the completed trace revision. A rejected or failed fill records `{ omittedReason: "credential" }`; the value must never enter an earlier trace revision, canonical buffer, mutation journal, API object, log, or client.
- Keep the existing host name check as an early rejection, but the guest's just-in-time classification remains authoritative. The guest returns classification and outcome metadata, never the submitted fill value; the broker already holds the value and releases it to the trace projection only after a non-sensitive success.
- Takeover mode produces no model or tool trace records. On return control, begin with the fresh observation already required by the browser capability boundary.
- Reuse the browser broker’s sensitive-target classification rather than maintaining a UI-only regular expression.
- Treat any value rejected by the browser capability boundary as non-traceable as well as non-executable.
- Strip URL credentials. Use the same query-free public URL already returned by browser observations; never trace internal page bindings or authorization-bearing headers.
- Represent a structurally omitted field with `{ omittedReason: "credential" }` rather than silently deleting the containing step.

Ordinary model-visible page text, public URLs, product names, prices, search queries, and non-sensitive form values remain verbatim. If an arbitrary public page prints a token-looking string in ordinary text and the existing browser observer allows it through, the trace will also show it; this feature does not add broad content redaction that differs from what the model saw.

Use explicit allowlisted projections rather than generic object copying:

| Boundary | Trace input/output |
| --- | --- |
| `observe`, `extract`, `scroll` | Validated operation fields and exact bounded broker result. |
| `navigate`, `click`, `select`, `keypress` | Public URL or resolved ref/target plus permitted argument; exact bounded result after execution. |
| `fill` | Ref/target at start; value only on completed, just-in-time-classified non-sensitive success. |
| Legacy `browser_program` | Safe operation label only. The production agent cannot call this compatibility path, so program source and result payloads are not traced in v1. |
| Approval | Public proposal, decision, expiry, and safe outcome; no hidden browser binding or submitted sensitive value. |
| Provider/model lifecycle | Turn timing/state only; no private reasoning, request headers, or provider response envelope. |

### Retention and limits

- Normalize trace payloads at capture time to an acyclic JSON-safe tree. Unsupported values become a typed placeholder. Measure UTF-8 bytes of the canonical compact JSON representation.
- Keep at most 500 trace steps and 2 MiB total: up to 1.5 MiB for canonical turns/steps and 512 KiB for the mutation journal, including labels and envelopes. Reserve 1 KiB outside that budget for one limit sentinel.
- Cap each serialized `input` or `output` at 64 KiB using deterministic structural truncation: visit keys/array elements in serialization order, stop before the byte cap, retain a valid JSON tree, and set `truncated: true` beside the detail.
- Evict the oldest completed turn first. Never evict an active turn unless the conversation stops.
- If one active turn reaches either conversation cap after per-payload truncation, stop recording new detail, insert one final **Trace limit reached; agent continued** step, and continue the agent run normally. Coalesce repeated progress updates before applying this limit.
- Preserve a stopped or failed turn for inspection while its conversation object remains in memory. Clear the buffer on Start over, conversation replacement/deletion, manager shutdown, or process restart.
- Do not write traces to `.open-muse/state.json`, generic logs, analytics, diagnostics, or error telemetry.
- The browser holds only the active conversation’s trace data in memory. A page reload can replay the current server buffer; a server restart cannot.
- Keep a mutation journal separate from the canonical step map: at most 1,000 events or 512 KiB, whichever comes first. Each journal upsert contains one full normalized turn or step revision, and its bytes count separately from the canonical map. Each buffer has a random `streamId`; track `oldestEventId` and `latestEventId` within that generation and compact old events without deleting canonical steps. A generation mismatch, a cursor older than `oldestEventId - 1`, or a cursor greater than `latestEventId` requires snapshot resync.

### API

Add two read-only endpoints under the existing authenticated session:

- `GET /api/conversations/:id/traces` returns `{ streamId, cursor, turns, limits }`, where `cursor` is the latest trace event ID in that stream generation.
- `GET /api/conversations/:id/traces/events` streams trace replacements as server-sent events and accepts `Last-Event-ID`.

Both routes use the same session authentication as conversation events. The existing loopback restriction remains in force. SSE IDs use `${streamId}:${eventId}`. A generation mismatch or out-of-range replay cursor triggers `trace.resync_required` with the current generation and cursor so the client refetches the snapshot. Replaying an event is idempotent because the client compares turn and step revisions.

If `response.write()` reports backpressure, unsubscribe that response immediately, stop sending it events, and end it on `drain`; native `EventSource` reconnects and resynchronizes. Do not maintain a second per-client queue.

Set `Cache-Control: no-store` on both routes. This design accepts the existing trust boundary in which another process running as the same local user can call loopback `/api/bootstrap` and obtain access to the active conversation; strengthening local-process isolation is a separate security change and must not be implied by this feature. Add tests that a non-loopback or unauthenticated request is rejected and that one conversation ID cannot read another conversation's trace.

Do not add raw trace fields to `GET /api/conversations/:id`, `/events`, or `/diagnostics`.

### Client

- Replace the `activities` projection in `App.tsx` with a `tracesByTurn` store.
- Subscribe to trace events alongside the existing conversation event stream.
- Render `TurnTrace` near the associated assistant turn, with a temporary placement after the user message while the response is pending.
- Use native `<details>`/`<summary>` for nested steps, enhanced with controlled state only where auto-expanding failures requires it.
- Render payloads as text using `JSON.stringify(value, null, 2)`. Never use raw HTML.
- Parse and store payloads immediately, but stringify and mount their DOM only when that individual step is expanded. Large payload blocks scroll horizontally and vertically within a bounded region.
- On screens below 720 px, the trace uses the full chat width, payloads cap at 50 viewport-height, and disclosure controls have at least 44 px touch targets.
- Preserve keyboard focus and expose `aria-expanded`, elapsed duration, step count, and failure state. Native disclosure controls respond to Enter and Space. Live count changes use a polite, throttled status announcement no more than once every two seconds. Respect reduced-motion settings and do not animate height changes.
- On trace-stream failure, keep the conversation usable and show a small **Run details unavailable** row. Trace observability must never block the agent.
- Derive the live timer from server timestamps and accumulated active duration; update it locally once per second without SSE timer events. Pause it during approval wait, clamp negative clock skew to zero, and stop it at `terminalAt`.
- Use distinct text and icons, not color alone, for running/failed/cancelled state. Announce terminal failure or cancellation once. Nested summaries include step number, label, and state; rely on native `<summary>` semantics instead of adding redundant manual `aria-expanded`.
- On first expansion in a conversation, show the compact cue **Run details may include page text and non-sensitive form values.** Do not turn it into a blocking dialog.

### Interaction states

| State | Collapsed label | Expanded behavior |
| --- | --- | --- |
| Empty/legacy | No trace row | Legacy messages render unchanged. |
| Starting | `Working · starting` | Shows no synthetic step until the first real boundary event. |
| Running | `Working · N steps · 6s` | Shows current steps; active step has a quiet progress indicator. |
| Waiting for approval | `Waiting for approval · N steps · 6s active` | Approval row shows the proposal; active-work timer is paused. |
| Completed | `Worked for 8s · N steps` | Successful child steps remain collapsed. |
| Failed | `Stopped after 6s · failed at step N` | Failed child opens only if the parent was already open. |
| Cancelled | `Stopped after 6s · N steps` | Final active step is marked cancelled. |
| Reconnecting | `Run details reconnecting…` | Existing steps remain readable; no spinner steals focus. |
| Resync required | `Refreshing run details…` | Fetch snapshot and reconcile by step revision. |
| Truncated | Normal turn label plus `Some details truncated` | Affected payload shows its truncation marker. |
| Evicted | `Earlier run details expired` | No expand control; conversation text remains intact. |
| Unavailable | `Run details unavailable` | No retry loop that affects the agent; reconnect on the next normal SSE attempt. |

### Example step counting

For the approved wireframe, **4 steps** means:

1. **Observed the page** — `browser_observe` input and returned snapshot in one row.
2. **Extracted page data** — `browser_extract` input and Markdown result in one row.
3. **Requested approval** — proposal plus approve/decline outcome in one row, if applicable.
4. **Used the result** — only when a distinct tool or verification boundary exists; model lifecycle never increments the visible count.

The overall active-work timer includes queue and execution time but excludes time spent waiting for the user's approval. It stops at assistant completion or, if no assistant message is produced, the failed/cancelled terminal transition. Child durations may overlap with the overall timer but not with each other because tool execution is sequential.

### Normative approval example

For user message `m7`, create turn `t7`. Observation tool `s1` starts at revision 1 and completes at revision 2 with its exact bounded observation. Action request tool `s2` starts, then completes with `{ approvalRequired: true, ... }`. Approval step `s3` starts, turn `t7` enters `waiting_for_approval`, and the active timer pauses. Approval updates `s3` to completed, resumes the timer, and approved execution creates tool step `s4`; a fill value appears only in `s4`'s completed revision after non-sensitive success. The resumed `agent.prompt()` remains under `t7` but creates no visible model step. The assistant message references `t7` and terminalizes it. Visible count is four. A decline instead cancels `s3` and `t7` and creates no `s4`.

### Terminalization matrix

| Manager path | Turn outcome | Started step outcome | Assistant required? |
| --- | --- | --- | --- |
| Normal response | completed | completed | yes |
| Agent/provider error or browser-start failure | failed | failed | no |
| User Stop or manager shutdown | cancelled | cancelled | no |
| New message supersedes active work | cancelled | cancelled | no |
| Take control during work | cancelled | cancelled | no |
| Approval declined/expired | cancelled | cancelled | no |
| Recovery interruption | remains open with failed step | failed | no; Continue resumes same turn |

Persist only the ownership metadata needed for recovery: checkpoint schema v4 adds optional `turnId` on messages and `recoveryTurn: { turnId, userMessageId }` on the stored conversation. Set `recoveryTurn` when accepting a user message and clear it only when that product turn reaches a normal terminal state; do not serialize `PendingApproval`, tool arguments, timing, or raw steps. Older checkpoints parse without either field. After a process restart, Continue reconstructs a fresh `TurnExecution` shell with the same IDs and zero prior in-memory steps, then labels the trace **Earlier run details expired** before adding new tool steps.

Approval creation schedules a manager-owned expiry timer for `expiresAt`; resolution, Stop, supersession, or shutdown cancels it. The submission path also checks expiry defensively. Whichever path observes expiry first atomically cancels the approval step and product turn once.

## Open Questions

- Whether a future explicit **Download trace** action should exist. It is out of scope because export changes the data-lifetime promise and needs its own confirmation design.

## Success Criteria

- During a run, the UI shows live elapsed time and step count within one second of a new trace step.
- Every model-visible browser tool input and result appears verbatim when expanded, subject only to the existing bounded browser payload limits.
- Structurally protected passwords, cookies, authorization headers, payment values, tokens, one-time codes, and takeover-only input never enter the trace buffer, API response, or DOM. Arbitrary ordinary page text follows the existing browser-observation policy.
- Completed traces remain collapsed by default and are associated with the correct assistant turn across rapid consecutive messages.
- Refreshing the client during a live session restores the current trace from the bounded server buffer.
- Restarting the server restores the conversation without restoring raw traces.
- Trace-stream failure does not interrupt messaging, browser control, approvals, or recovery.
- On a reference 4-core laptop in a production build, ingesting and reconciling a worst-case 2 MiB snapshot takes under 100 ms scripting time and keeps any single main-thread task below 50 ms; only an expanded payload is pretty-printed and mounted.
- Tests prove trace data never enters checkpoints, diagnostics, console/error logging, analytics, React error payloads, `localStorage`, `sessionStorage`, IndexedDB, or service-worker caches.
- Rejected sensitive fills prove the submitted value never appears in any intermediate trace event, replay journal, serialized response, DOM, or log sink.
- Race tests cover supersession during model work, browser startup, approval creation, approval resolution, and recovery continuation; stale executions never append an assistant message or overwrite current run state.
- Accessibility tests cover focus retention, throttled announcements, terminal-state announcements, keyboard disclosure, and navigation inside a maximum-size payload block.
- Existing browser capability, checkpoint, diagnostics, and E2E suites continue to pass.

## Reviewer Concerns

The third independent review scored the pre-closure draft 6.2/10 and did not recommend approval until two blockers were made explicit: execution identity with a reused agent/broker, and just-in-time sensitive-field classification. This revision addresses them with async-scoped execution identity plus entry and post-`await` fences, and by withholding every fill value until the guest classifies and successfully fills the field in one operation. It also closes the review's event, counting, recovery, expiry, projection, accounting, privacy-cue, and accessibility gaps. These final edits were not sent through a fourth independent office-hours pass because that workflow caps the adversarial loop at three iterations; the subsequent engineering review and outside voice made the race and non-retention tests mandatory acceptance gates.

## What Already Exists

- `ActionBroker` already validates structured browser operations, resolves short-lived refs, enforces approval, and owns the authoritative host-side sensitive-target check. Reuse it for safe trace projections.
- The guest Playwright program already revalidates page identity and inspects fill-field `type`/`autocomplete` immediately before acting. Extend its result shape instead of adding a second classifier.
- `ConversationManager` already serializes prompts, aborts superseded work, checkpoints recovery, and publishes bounded sanitized events. Add explicit execution ownership without replacing that lifecycle.
- The authenticated conversation SSE route already implements heartbeats and native `Last-Event-ID` parsing. Extract a shared stream writer and add trace-specific generation/resync behavior.
- The client already maps conversation messages, listens with `EventSource`, and renders the **Live activity** panel. Replace that projection; do not introduce a state library.
- Node 22 provides stable `AsyncLocalStorage.run()`, and browsers provide native `EventSource` reconnect behavior. No new dependency is required.

## NOT in Scope

- Hidden chain-of-thought or provider-private reasoning, because the provider does not expose it and tool-boundary data answers the user need.
- Durable raw trace persistence, trace export/download, analytics, diagnostics, or browser storage; these change the agreed data-lifetime promise.
- Raw payload capture for dormant legacy `browser_program` operations; v1 records only a safe compatibility label.
- Stronger isolation between local operating-system processes and `/api/bootstrap`; that is a separate session-security project.
- A new Playwright trace UI suite in this PR. D7 chose unit plus server integration coverage; create the approved P2 TODO and keep a manual visual acceptance pass.
- Multi-conversation trace storage or a new service/database. OpenMuse still owns one active local conversation.

## Failure Modes and Coverage

| Path | Production failure | Handling | Required coverage |
| --- | --- | --- | --- |
| Trace normalization | Cyclic or unsupported result | Valid JSON placeholder or fail-open sentinel; agent continues | Unit |
| Size accounting | Active turn exceeds cap | Reserve and insert one limit sentinel; stop new capture | Unit |
| Supersession | Old queued/awaited run resumes | Entry and post-await fences allow only self-cancellation | Manager integration |
| Approval resume | HTTP path bypasses tool wrapper | Explicit execution-bound trace transaction | Manager integration |
| Approval expiry | Timer and submit race | Atomic once-only cancellation; clear timer on every terminal path | Unit + manager integration |
| Sensitive fill | Field changes during approval | Guest classifies immediately before fill; value released only on explicit ordinary success | Broker integration |
| Recorder fault | Normalizer/accounting throws | Disable only that turn's capture; preserve tool result | Unit + manager integration |
| Subscriber fault | Listener throws or tab stalls | Eject that subscriber; backpressure closes and reconnects | Route integration |
| Server restart | Old cursor overlaps new IDs | `streamId` mismatch forces snapshot resync | Route integration |
| Large client payload | Rendering blocks chat | Store parsed data, pretty-print/mount only expanded step | Reducer/helper unit + manual browser pass |
| Trace endpoint failure | Snapshot/SSE unavailable | Conversation remains usable; show **Run details unavailable** | Route integration + manual browser pass |

No planned failure remains silent without handling and a test. The two visual-only behaviors excluded by D7 are covered manually and tracked in the P2 Playwright TODO.

## Worktree Parallelization

| Step | Modules touched | Depends on |
| --- | --- | --- |
| Trace contract and buffer | `open-muse/server/`, server unit tests | — |
| Tool, broker, and fill safety | `open-muse/server/`, broker tests | Trace contract |
| Manager lifecycle and routes | `open-muse/server/`, route/manager tests | Trace contract; broker safety |
| Client reducer and disclosure | `open-muse/client/`, client unit tests | Trace contract |
| Cross-boundary integration | `open-muse/test/` | Server and client lanes merged |

Lane A: trace contract → tool/broker safety → manager/routes, sequential because all modify `open-muse/server/`.

Lane B: client reducer/disclosure can begin after the trace contract is fixed and run in parallel with Lane A's broker/manager work.

Merge Lane A and Lane B, then run cross-boundary integration and the manual browser pass. The only conflict risk is shared public trace types; freeze that schema in the first step before parallel work starts.
