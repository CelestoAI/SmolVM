# Design: OpenMuse — General Web Operator

OpenMuse lets a person ask for work in chat, watch it operate public websites inside a disposable computer, and take control whenever human input is needed.

> **Current implementation:** The example exposes only structured browser operations to the production model.
>
> - Bounded, redacted observation and scrolling run directly.
> - Navigation, click, fill, select, and keypress requests require one-time approval bound to the current tab epoch, page, and exact normalized arguments. Approved operations have durable `approved`, `dispatched`, `completed`, and `outcome_unknown` states and are never replayed after uncertainty.
> - Popups are quarantined until explicit adoption. Takeover pauses every owned tab. Raw `browser_run` remains internal and is not exposed to the production model because a real Playwright `Page` can reach its browser context; exposure waits for the brokered guest-side page facade described below.
> - SmolVM now has private public-egress building blocks: connection-time DNS classification, pinned upstream connections, a per-session proxy, TAP restrictions, QEMU restricted forwarding, and Chromium proxy plumbing. The public API and OpenMuse switch remain gated on real Firecracker and QEMU attack-suite smokes and image release pins.
> - SmolVM now has an internal, unintegrated browser-profile artifact store with versioned manifests, exclusive locking, private permissions, atomic generation saves, bounded retention, and explicit reset and migration. Authenticated OpenMuse sessions remain gated on egress enforcement, masking, takeover, and profile integration.

## Problem Statement

The current OpenMuse implementation proves the UI and SmolVM browser lifecycle against `shop.smol.test`, but its agent tools, intent model, and network policy are tied to that synthetic store. OpenMuse should instead operate arbitrary public websites through a real browser in its disposable SmolVM. Amazon is one example, not a special integration.

## What Makes This Cool

The same open-ended chat can research, shop, fill forms, and operate web applications while the user watches the exact browser. There are no required per-site adapters. A developer can see that SmolVM is the computer boundary and Pi plus Playwright is the general agent harness.

## Constraints

- Keep Pi as the conversational agent harness.
- Run model-written Playwright programs inside the disposable VM, next to Chromium. The host sends programs over a narrow runner RPC and never evaluates model code in the Node process that holds the model API key.
- Enable public HTTP and HTTPS navigation through a VM egress proxy that owns DNS resolution and each connection. Reject loopback, link-local, private, reserved, metadata-service, `file:`, `chrome:`, and other non-public destinations on every redirect and subresource.
- Keep `shop.smol.test` as a deterministic network-off test fixture, not as the production browser boundary.
- Use risk-based approvals with a conservative unknown-site default: passive observation and scrolling flow without interruption; every active interaction pauses immediately before execution unless trusted policy can prove it safe. Navigation is auto-allowed only when its canonical URL exactly matches a URL in the current user message; model- or page-discovered destinations require approval.
- Credentials are entered by the user through takeover. The agent must not receive password values, payment credentials, or authentication cookies.
- A sandbox protects the host and filesystem. It does not undo changes made to a logged-in website, so sending, publishing, deleting, booking, checkout, payment, and equivalent effects still require explicit approval.

## Premises

- The correct product abstraction is a browser-capable sandbox, not a collection of website adapters.
- Direct Playwright is acceptable because both the controlled browser and the model-written program live in SmolVM and the agent receives no host execution capability.
- Site-specific knowledge may improve prompts or tests later, but no adapter is required to visit or operate a site.
- Human takeover plus a persistent SmolVM browser profile is the login path; importing the user's host Chrome profile is not required.
- Approval policy is domain-independent. Unknown sites are authorized at the browser-operation level; optional trusted integrations may later provide stronger semantic authorization without becoming prerequisites for site access.

## Approaches Considered

- **Structured browser tools:** generic `observe`, `click`, and `type` primitives offer tighter control but constrain the agent to the wrapper's feature set.
- **Direct Playwright (selected):** Pi submits Playwright browser programs to a runner inside the owned SmolVM browser session. This provides the broadest website compatibility and keeps model-written code out of the host server.
- **Visual-only computer use:** coordinate actions work on unusual pages but are slower and less reliable, so screenshots are a fallback rather than the primary API.

## Recommended Approach

Replace the store-specific Pi tools with one `browser_run` tool. It accepts a bounded JavaScript Playwright program plus a short declared action summary. The program runs as an unprivileged `agent` process inside the disposable VM. Chromium and its profile run as a separate `browser` user; the runner cannot read the browser profile, guest-agent state, or host credentials. A broker-owned local RPC supplies one Playwright-connected `page` capability. The runner has no host filesystem, model API key, SmolVM control credential, Docker socket, or host-mounted workspace.

The runner uses a Playwright-shaped scripting surface rather than an unrestricted Node module graph. It supports `page.goto`, locator queries and assertions, clicks, fill/type, selection, keyboard and mouse input, scrolling, screenshots, bounded page text, and owned tabs. It excludes `require`/`import`, `process`, filesystem and socket APIs, arbitrary CDP, cookies/storage/header extraction, external protocols, downloads in the first milestone, and browser-internal pages. Programs are limited to 30 seconds, 100 browser operations, one effect-capable call at a time, 64 MiB of heap, and 256 KiB of returned JSON. Screenshots are downscaled, size-capped artifacts referenced by opaque ID rather than embedded in JSON. Raw page content is labeled untrusted.

```text
Pi agent
  │ browser_run(program, summary)
  ▼
Host broker ───────────── approval card / user decision
  │ authenticated per-session vsock RPC        ▲
  ▼                                             │ suspend one RPC
Guest runner process → frozen scripting realm → brokered page facade
                                                  │
                                                  ▼
                                  guest Playwright owner → Chromium
```

The guest runner parses programs with an allowlisted AST grammar: expressions, bounded loops, local variables, `await`, and calls on the supplied facade only. It rejects dynamic property access on capabilities, constructors, prototype mutation, dynamic code generation, modules, callbacks crossing the RPC boundary, and background promises. The realm starts with frozen prototypes and no ambient globals beyond inert language primitives. A per-session random capability authenticates the Unix-socket or vsock transport. Messages are length-prefixed, schema-validated request/response records with a monotonic operation number. The runner tracks every facade thenable and accepts completion only when all have settled; any un-awaited active operation aborts the program. Process teardown closes the transport and invalidates the capability. Release tests prove the `agent` user cannot connect directly to CDP, read browser-profile paths, or invoke a facade operation without a matching broker decision.

Before executing an active Playwright operation, the RPC asks the host action broker for a decision. Page labels and the model's summary are untrusted display context, never authorization evidence. The deterministic default policy is:

- `allow` for observation, locator resolution, screenshots with sensitive-field masking, scrolling, and a canonical public URL supplied verbatim by the current user;
- `approve` for model- or page-discovered navigation, click, fill/type, select, keypress, mouse/drag/drop, and dialog or popup interaction; later stages add uploads and downloads to this class;
- `deny` for credential extraction, payment entry, CAPTCHA circumvention, private-network access, and browser-internal pages. Whether an approved operation satisfies the broader request remains model judgment, not a broker security claim.

```ts
type ProposedBrowserOperation = {
  operationId: string;
  conversationId: string;
  origin: string;
  tabId: string;
  tabEpoch: number;
  frameId: string;
  frameEpoch: number;
  kind: "navigate" | "click" | "fill" | "select" | "keypress" | "mouse" | "dialog" | "popup" | "upload" | "download";
  arguments: Record<string, string | number | boolean>; // normalized and secret-redacted
  target?: { role?: string; name?: string; attributes: Record<string, string>; context: string };
};

type PendingApproval = {
  approvalId: string;
  operationDigest: string;
  operation: ProposedBrowserOperation;
  displaySummary: string; // untrusted context, clearly labeled in the UI
  state: "pending" | "approved" | "rejected" | "expired" | "invalidated" | "dispatched" | "outcome_unknown" | "completed";
  expiresAt: string;
};
```

Only `pending` may resolve to `approved` or `rejected`; duplicate decisions return the current state. `approved` becomes `dispatched` only after digest, epoch, target, ownership, and expiry revalidation. It then becomes `completed` or `outcome_unknown` and is never reusable. New input, takeover, target mismatch, or navigation makes it `invalidated`. The approval card shows origin, operation, redacted target, redacted arguments, and the untrusted summary; it never renders page HTML.

An approved action is bound to the origin, tab and frame navigation epochs, operation, normalized arguments, and a target snapshot containing role, accessible name, stable attributes, and visible surrounding text. The broker re-resolves and compares the target immediately before dispatch. This authorizes one browser operation, not a guaranteed real-world effect. A trusted integration is required for stronger claims such as an exact product, price, recipient, or repository mutation.

Only one facade RPC may be in flight. Parallel effect-capable calls and un-awaited active operations are rejected. When approval is pending, all later dispatch is blocked. Rejection aborts the program at that operation. New user input, takeover, navigation epoch change, or timeout aborts the whole program. After a runner or connection crash, the UI reports **The last website action may have completed; check the browser before retrying**, and the agent never retries automatically.

The VM egress proxy resolves DNS itself, connects only to the validated IP, and repeats validation for redirects and subresources. Direct guest DNS, QUIC, WebRTC, raw sockets, external protocols, and proxy bypasses are blocked. HTTP, HTTPS, WebSocket, and service-worker requests all traverse the proxy; IPv4 and IPv6 private, reserved, loopback, link-local, multicast, and metadata ranges are denied.

Each tab has an owner and navigation epoch. New popups are quarantined until their public destination is validated, then become agent-owned tabs. Approvals bind to one tab. Takeover pauses every tab; return-to-agent forces fresh observation of all open tabs. The agent cannot close a human-owned tab without approval.

During takeover, all model observations stop. Before resuming, the broker masks password and payment inputs, blocks cookie/storage/header and clipboard APIs, disables autofill inspection, and refuses screenshots while a sensitive input contains a value. Accessibility snapshots, locator text/value reads, returned JSON, approval snapshots, logs, and errors never include sensitive input values. A sensitive input is any password control, payment/autocomplete field, or control marked sensitive by Chromium. The UI explains that other page content and screenshots sent to the configured model provider remain subject to that provider's retention terms.

Persistent login remains deferred. SmolVM now has the dedicated, versioned browser-profile artifact store, but OpenMuse does not use it yet. The current persistent mode retains the whole VM disk and must not be used for this authenticated example. Ephemeral login through takeover is permitted for local evaluation.

### Delivery stages

1. **Read-only public web:** hardened egress plus the in-VM runner; only observation, scroll, and exact user-supplied URL navigation. Redirects and page-load effects remain a disclosed residual risk.
2. **Ephemeral interaction:** every active operation requires one-time approval; no uploads or downloads.
3. **Authenticated profiles:** dedicated profile storage and sensitive-observation controls.
4. **Lower-friction policy:** optional trusted integrations may auto-allow semantically proven operations, while unknown sites keep operation-level approvals.
5. **Compatibility expansion:** uploads, downloads, cross-origin frames, and visual fallback.

CAPTCHAs, browser-attestation challenges, anti-bot blocks, DRM surfaces, and sites that prohibit automation are explicit non-goals. “Any website” means no required site adapter, not a guarantee that every site will permit automation.

## Success Criteria

- A prompt containing a URL can open and operate an arbitrary public website without code changes or a site adapter.
- The agent can complete a cross-site read-only task using navigation, tabs, and page inspection.
- With user takeover for ephemeral login, the agent can add a requested item to a cart on a real commerce site and pauses immediately before the click that may mutate the cart.
- The agent cannot reach host services, private IP ranges, instance metadata, local files, browser internals, or arbitrary Node APIs.
- Deterministic malicious fixtures cover commerce, webmail, issue tracking, runner escape attempts, redirects, DNS rebinding, IPv6, service workers, WebSockets, popup effects, DOM churn during approval, concurrency, crashes, and secret leakage.
- Property tests exercise generated runner programs, and real-VM smoke tests run on each supported backend.
- CI remains deterministic and never signs into or mutates a real external account.

## Distribution Plan

The UI remains the repository's top-level `open-muse` app, but the capability requires first-class platform work: browser-image user separation, guest runner and egress-proxy packaging, runtime protocol negotiation, TypeScript SDK support, and a dedicated example workflow. Image releases follow the repository checklist: build and smoke each backend, publish the guest and rootfs artifacts, update the rootfs and guest-agent SHA pins, and only then tag the SmolVM package. CI builds the app, runs fixture/policy tests, and smokes the released image on every supported backend. Real-site tests remain opt-in local evaluations.

## Next Steps

1. Build and smoke the private public-egress path against the complete attack matrix on Firecracker/TAP and QEMU/slirp, then publish and pin the tested browser images.
2. Expose public-only networking in Python, TypeScript, OpenAPI, and capability negotiation together; switch OpenMuse from `open` to `public` without fallback.
3. Replace the raw Playwright `Page` with the brokered guest-side facade before re-exposing `browser_run`.
4. Add policy-bound uploads, quarantined downloads, and masked visual fallback on the proven tab and egress boundaries.
5. Integrate the dedicated profile artifact with authenticated sessions only after the egress, masking, takeover, and artifact migration gates pass.
