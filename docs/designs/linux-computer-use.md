# Linux computer-use template

SmolVM should let a developer start a familiar Linux desktop for an agent, watch it work, take control when needed, and automate Chromium without assembling a display stack themselves.

Generated by `/office-hours` on 2026-09-14  
Branch: `design/linux-computer-use`  
Repo: `CelestoAI/SmolVM`  
Status: READY FOR APPROVAL  
Mode: Builder

## Problem statement

The current browser session already exposes the full graphical framebuffer through noVNC and VNC, but its image and public API are browser-focused. In `desktop` mode it starts Xvfb, Openbox, x11vnc, and websockify, then deliberately skips Chromium. Because the image has no panel, terminal, file manager, or editor, the result is technically a desktop but visually an empty Openbox workspace.

Developers should not need to know that history. They need one obvious way to ask for an interactive computer and receive a ready object with:

- a live view for a person;
- a VNC endpoint for coordinate-based computer-use agents;
- a CDP endpoint for reliable Chromium automation;
- command execution and file transfer;
- a predictable set of useful desktop and command-line tools;
- one cleanup operation that deletes the complete computer.

Linux is the first supported template. Windows and macOS must fit the same public model later, but they are not implementation scope for this release.

## Product decision

Add a first-class `computers` resource. A computer is an interactive sandbox with a graphical display, commands, and files. A template selects its operating system image and guaranteed capabilities.

The first template is `linux-desktop`. It guarantees a graphical display and Chromium automation. Existing browser APIs remain available and use the same lifecycle implementation, but `browsers.create()` is not the public entry point for general desktop work.

Rejected alternatives:

- Generic `sandboxes.create({ template })`: rejected because it makes display and automation endpoints optional on the most common sandbox type and weakens type clarity.
- Expanding only `browsers.create({ mode: "desktop" })`: rejected because it makes a full Linux computer sound like a browser option and gives Windows and macOS no durable home.

## Product vocabulary

Each public resource answers one user question:

| Resource | Use it when | Guaranteed surface |
|---|---|---|
| `sandbox` | “I need to run commands or manipulate files.” | exec, files, networking |
| `browser` | “I need to automate websites.” | Chromium and CDP; an optional live view does not make it a general desktop |
| `computer` | “I need to see or operate a graphical desktop and its applications.” | display, input, exec, files, plus template capabilities such as Chromium CDP |

A computer contains applications; it does not contain another billable or independently deletable SmolVM resource. `computer.browser` is a handle to Chromium running inside that same computer. Deleting the computer deletes the browser with it. Users never call `SmolVM.browser()` and `SmolVM.computer()` for the same VM.

The choice rule in every guide is:

1. Choose `browser` for web-only automation, even when a person needs to watch it.
2. Choose `computer` when the task needs a desktop, GUI applications, VNC-style input, or movement between browser and non-browser applications.
3. Choose `sandbox` when no graphical interface is needed.

Do not introduce “desktop session,” “graphical sandbox,” or “browser computer” as additional public product names. Those terms may describe internals but must not appear as competing SDK entry points.

### Compatibility names without product confusion

- `SmolVM.browser(headless=False)` remains a visible browser. It has a viewer because supervision is useful, but it does not promise a panel, terminal, file manager, or general desktop.
- Python `SmolVM.desktop()` remains a legacy low-level display factory for compatibility. It is omitted from new quickstarts and points readers to `SmolVM.computer()` when they want a usable desktop.
- `mode="desktop"` remains accepted where it already exists but is not added to new APIs. A computer has no `headless` flag; callers needing headless Chromium use `browser`.
- `computer.browser` never creates another VM. It only controls the browser application installed by the selected computer template.

### Edge cases and required behavior

| Situation | Required behavior |
|---|---|
| User requests `headless=True` on a computer | Reject before allocation: `Computers are visible desktops; call SmolVM.browser(headless=True) instead.` |
| User needs only a watched website | Documentation recommends a visible `browser`; watching pixels alone does not require a `computer`. |
| User closes Chromium from the desktop | Keep the computer ready, report `computer.browser.status == "closed"`, set its CDP URL to `null`, and allow an explicit idempotent `launch()`. |
| User closes Terminal, Files, or Text Editor | Keep the computer ready; applications can be reopened from the menu without changing endpoints. |
| A critical display process dies after startup | The affected endpoint stops working. V1 does not emit a background health event; inspect logs, delete the computer, and create another one. |
| Browser launch fails but the desktop still works | Keep the computer ready with `computer.browser.status == "error"`; return a browser-specific recovery instead of declaring the whole VM dead. |
| Human and agent send input simultaneously | Do not pretend SmolVM arbitrates control. Both inputs reach the same display; the embedding application must provide a control lease when exclusivity matters. |
| Human refreshes or closes the viewer | Keep the computer and applications running; reconnecting the same viewer restores the current pixels. |
| User resizes the viewer window | Scale the viewer only. Guest resolution and coordinate space stay fixed for the computer's lifetime. |
| Multiple viewers connect | Show the same display and shared cursor state. Document that concurrent control can conflict. |
| Multiple computers are created | Give each independent VM, ports, profile, downloads, and immutable computer ID; never reuse a live endpoint. |
| A requested name already exists or two creates race | Allocate at most one VM and reject the loser before image or network allocation. |
| Network mode is `off` | Start the desktop normally; browser navigation fails with a network-policy message, not a browser-start failure. |
| A website shows CAPTCHA, sign-in, download, or system dialog | Leave it visible for human intervention. SmolVM exposes the computer but does not claim the site permits automation. |
| Chromium opens several windows or profiles | CDP addresses the template-owned default profile. User-created secondary profiles are visible but not guaranteed as automation targets in v1. |
| Future template has no browser capability | Its typed session omits `computer.browser`; callers must check template capabilities before using optional applications. `linux-desktop` guarantees it. |
| `delete()` races with exec, file transfer, CDP, or viewer input | Stop accepting new operations, cancel or bound active work, then clean resources once. Every later operation returns the deleted-state error. |
| SDK process is killed | The pre-allocation ownership journal lets the next SDK or CLI invocation find and reconcile leftover resources. |
| Host-mounted workspace cannot be written as `agent` | Fail readiness with the exact mount path and recovery; do not silently fall back to root-owned files. |
| Endpoint is copied to another machine | Connection fails because it is loopback-only. Remote access requires an explicit future authenticated feature. |

The documentation should present one decision table once, then use only the chosen noun throughout each guide. A browser guide should not call its resource a computer, and a computer guide should describe Chromium as an application inside the computer.

## Documentation structure

The public documentation ships with the feature and mirrors the SDK grouping exactly. Do not publish examples for an API that has not shipped.

### Choose the resource first

The SDK overview and README show the same three-row decision table from this design before introducing individual APIs:

- Use a sandbox for commands and files.
- Use a browser for websites.
- Use a computer for a visible desktop and GUI applications.

Each sentence links to one focused guide. The guides do not repeat competing terms or ask readers to understand Xvfb, VNC, CDP, or the graphical-session implementation before they choose.

### Compatibility documentation

The Browser guide says that `headless=False` adds a live view but does not turn the browser into a general Linux desktop. The Computers guide mentions `SmolVM.desktop()` only in a short Python migration note and labels it a legacy low-level display factory, not a fourth resource. Existing browser and desktop documentation remains unchanged until the computer API is released; the release PR updates links and examples atomically with the implementation.

Every error example uses the noun and recovery call for its surface. Browser failures point to browser creation, computer browser-application failures point to `computer.browser.launch()`, and complete desktop failures point to computer deletion and recreation.

## Intended users

The primary user is an application developer building a computer-using agent. They want to give the agent a disposable machine without becoming an expert in Linux desktops, VNC, display servers, image construction, or port forwarding.

The secondary user is a person supervising that agent. They want to see real pixels, understand whether the machine is ready, take control, and return control without losing the running session.

## User experience

### Starting state

When the computer becomes `ready`, its live view shows a recognizable desktop rather than an empty gray screen:

1. Chromium is open and maximized on a neutral new tab.
2. A lightweight panel remains visible with an application menu, open windows, and clock.
3. The application menu contains Chromium, Terminal, Files, and Text Editor.
4. `/workspace` is the default directory in Terminal and Files.
5. The screen uses the requested resolution and scales in noVNC.

The desktop should feel plain and trustworthy. Do not imitate a branded consumer operating system or add a custom launcher. Familiar Linux controls are preferable to bespoke UI.

### Human supervision

`computer.display.viewerUrl` opens noVNC in a browser. `computer.display.vncUrl` connects a VNC client or a computer-use agent directly. The live display must survive viewer refreshes and temporary websocket disconnects without restarting the computer or losing application state.

SmolVM itself does not arbitrate human-versus-agent input in the first release. The SDK exposes one display. Applications such as OpenMuse retain responsibility for their control lease, input shield, and takeover workflow.

### Ready, error, and deleted states

- `starting`: the VM or graphical session is still booting. Endpoints are not returned as usable.
- `ready`: display, VNC, Chromium CDP, command execution, and files have all passed readiness checks.
- `error`: startup failed, diagnostic logs remain available, and best-effort cleanup ran. The error names the exact delete and retry commands.
- `stopping`: new operations are rejected while cleanup runs.
- `deleted`: the computer and ephemeral state are gone. Repeated deletion succeeds.

A partly ready computer must never be returned. For example, an available VNC port with a dead window manager is a creation failure, not success.

## Developer experience

### TypeScript

The basic path should be four conceptual steps: create, use endpoints, do work, close.

```ts
import { chromium } from "playwright-core";
import { SmolVM } from "@celestoai/smolvm";

const smolvm = new SmolVM();
const computer = await smolvm.computers.create({
  template: "linux-desktop",
  display: { width: 1440, height: 900 },
});

try {
  const browser = await chromium.connectOverCDP(computer.browser.cdpUrl);
  const page = browser.contexts()[0]?.pages()[0];
  if (!page) throw new Error("The Linux computer did not open Chromium.");
  await page.goto("https://example.com");

  await computer.files.write("/workspace/task.txt", "done");
  console.log(computer.display.viewerUrl);
} finally {
  await smolvm.close();
}
```

Proposed surface:

```ts
type ComputerTemplate = "linux-desktop";
type ComputerSessionStatus =
  | "ready"
  | "error"
  | "stopping"
  | "deleted";
type ComputerCapability =
  | "display.viewer"
  | "display.vnc"
  | "browser.cdp"
  | "sandbox.exec"
  | "sandbox.files"
  | "computer.events";

type CreateComputerOptions = {
  template: ComputerTemplate;
  name?: string;
  backend?: "auto" | "qemu" | "firecracker";
  display?: { width?: number; height?: number };
  resources?: { memoryMiB?: number; diskMiB?: number; vcpus?: number };
  network?: NetworkPolicy;
  workspace?: WorkspaceMount[];
};

interface ComputerSession {
  readonly computerId: string;
  readonly sandboxId: string;
  readonly template: ComputerTemplate;
  readonly status: ComputerSessionStatus;
  readonly capabilities: readonly ComputerCapability[];
  readonly display: {
    readonly viewerUrl: string;
    readonly vncUrl: string;
  };
  readonly browser: {
    readonly status: "ready" | "closed" | "error";
    readonly cdpUrl: string | null;
    launch(): Promise<void>;
  };
  readonly files: RemoteFiles;
  exec(command: string | string[], options?: ExecOptions): Promise<ExecResult>;
  delete(): Promise<void>;
}

interface ComputerCollection {
  create(options: CreateComputerOptions): Promise<ComputerSession>;
}
```

`linux-desktop` is the only accepted value initially. The union remains intentionally closed so a misspelled or unreleased template fails before a VM is created.

### Python

```python
from smolvm import SmolVM

with SmolVM.computer(template="linux-desktop") as computer:
    print(computer.display.viewer_url)
    computer.run("python3 --version")
```

The Python contract is deliberately parallel to TypeScript:

```python
computer = SmolVM.computer(
    template="linux-desktop",
    name="demo",
    backend="auto",
    display={"width": 1440, "height": 900},
    resources={"memory_mib": 2048, "disk_mib": 8192, "vcpus": 2},
    network={"mode": "open"},
    workspace=[...],
    on_event=lambda event: print(event["type"]),
)
computer.computer_id
computer.sandbox_id
computer.status
computer.capabilities
computer.display.viewer_url
computer.display.vnc_url
computer.browser.status
computer.browser.cdp_url
computer.browser.launch()
computer.files
computer.run(...)
computer.delete()
```

`SmolVM.computer(...)` is a new class factory, matching the existing `SmolVM.browser(...)` and `SmolVM.desktop(...)` style without calling `SmolVM()` and accidentally creating an unrelated default VM. `on_event: Callable[[ComputerEvent], None] | None` receives the same ordered, best-effort event union as TypeScript. The context manager calls `delete()` on exit. `delete()` is idempotent and retryable after cleanup failure. Cross-process inventory remains a CLI concern in normal operation.

### CLI

Commands follow the repository's noun-verb convention:

```bash
smolvm computer start --template linux-desktop --name demo
smolvm computer open demo
smolvm computer list
smolvm computer logs demo
smolvm computer delete demo
smolvm computer templates
```

`start` prints the computer ID, sandbox ID, template, status, viewer URL, display URL, and CDP URL. `open` opens the loopback noVNC viewer. JSON output carries the same fields without human-only formatting. A CLI-created computer remains available after the command exits and is removed only by `computer delete`. There is no `stop` or `restart` command in v1 because deletion is the only supported terminal operation.

`--name` supplies the immutable `computerId`; there is no second public name field. If omitted, SmolVM generates `computer-<8 lowercase hex characters>`. IDs use the existing runtime identifier pattern, must be unique among non-deleted computers, and are accepted anywhere the CLI shows `demo`. A collision fails before creating a VM. `sandboxId` remains a separate implementation identifier and is not accepted as a computer CLI target.

### Defaults

- Template: required in the first API version, even though only one exists. This keeps future OS selection explicit.
- Display: `1440 × 900`.
- Memory: `2048 MiB`.
- vCPUs: `2`; creation fails with a short actionable error if the selected backend cannot provide them.
- Disk: `8192 MiB`, because desktop packages and downloads need more room than the current browser image.
- Backend: `auto`, choosing QEMU or Firecracker through the existing runtime rules. `libkrun` is excluded from the v1 type and rejected before image allocation.
- Network: `open`, matching the current TypeScript browser default. The docs state plainly that this lets the computer reach the public internet; existing private-network and metadata-address protections still apply.
- State: ephemeral. Persistent desktop state is not included in the first release.
- Lifetime: no TTL in v1. A TypeScript computer is deleted by its handle or the owning client's `close()`; a Python computer is deleted by its handle or context-manager exit. CLI-created computers remain in the local registry until `smolvm computer delete <id>` succeeds.

### Errors

Every public failure states the fact and the exact recovery for the surface that raised it. CLI failures retain a local inventory record and may name `computer logs` or `computer delete`. SDK failures do not name CLI commands when cleanup succeeded; they include a bounded, endpoint-redacted diagnostic summary and name the relevant TypeScript or Python call.

| Surface and failure | Message shape |
|---|---|
| CLI unknown template | `Computer template 'foo' is unavailable; run 'smolvm computer templates' to list supported templates.` |
| CLI name collision | `Computer 'demo' already exists; run 'smolvm computer delete demo' or choose another name.` |
| CLI display failure | `Linux computer 'demo' did not start its desktop; run 'smolvm computer logs demo', then 'smolvm computer delete demo'.` |
| TypeScript create failure, cleanup complete | `Linux computer 'demo' did not start Chromium; fix the reported problem and call smolvm.computers.create() again.` |
| Python create failure, cleanup complete | `Linux computer 'demo' did not start Chromium; fix the reported problem and call SmolVM.computer() again.` |
| SDK deleted handle | `Computer 'demo' has been deleted; create another computer before retrying this operation.` |
| SDK delete incomplete | `Computer 'demo' was not fully deleted; call computer.delete() again.` |
| Unsupported runtime | `This SmolVM runtime cannot create computers; run 'curl -sSL https://celesto.ai/install.sh \| bash' to update it.` |

If SDK cleanup cannot finish before its owner exits normally, it promotes the existing ownership-journal entry—with only unresolved resource IDs and a redacted diagnostic path—to the CLI inventory as an `error` record. After an abrupt crash, the next SDK or CLI startup performs that promotion from the pre-existing journal. The surfaced error names `smolvm computer delete <id>` as the recovery. `logs`, `delete`, and `templates` ship in v1, so those exceptional recovery commands exist.

## Linux template contents

### Graphical applications

- Chromium: browser and CDP automation target.
- LXTerminal: lightweight terminal emulator, opening in `/workspace`.
- PCManFM: lightweight file manager, opening in `/workspace`.
- Mousepad: lightweight text editor.
- Tint2: taskbar, application menu access, window list, and clock.
- Openbox: existing window manager.

Do not include VS Code, an office suite, media applications, or a full GNOME/KDE/XFCE desktop in this release. They substantially increase image size and startup surface without improving the core computer-use workflow.

### Command-line tools

- bash, coreutils, procps, iproute2
- curl, wget, ca-certificates
- git, openssh-client
- Python 3 and pip
- Node.js and npm
- jq
- tar, gzip, zip, unzip

Versions follow the base image except where SmolVM already pins a tool for compatibility.

### Desktop session

All graphical applications and SDK `exec` commands run as the existing unprivileged `agent` user. This keeps files created through the terminal, CDP downloads, the file manager, and `computer.files` mutually accessible without broad permissions. The browser-only image keeps its existing `browser` identity. The session starts in this order:

```text
Xvfb :99
  ├── dbus session
  ├── Openbox
  ├── Tint2
  ├── Chromium with remote debugging on guest loopback
  ├── x11vnc
  └── websockify + noVNC
```

The root-owned supervisor owns PID files and logs. The `agent` user owns its home, ephemeral Chromium profile, downloads, and `/workspace` only where existing mount permissions permit it.

Computer-scoped file writes do not use the generic root-owned write behavior unchanged. The guest agent performs their open, atomic rename, and ownership steps as `agent:agent`, preserving the requested mode. A writable host workspace is preflighted with an `agent` create/overwrite/delete probe during readiness; creation fails if its UID/GID mapping cannot support the same behavior. This change is scoped to computer files and does not alter generic sandbox file semantics.

Use a small checked-in Openbox menu and Tint2 configuration. Avoid a second init system inside the image. The existing `smolvm-browser-session` script should be extracted into a graphical-session helper shared by browser and computer templates rather than copied.

## Architecture

```text
TypeScript / Python / CLI
          │
          ▼
   Computer collection
          │ create(template="linux-desktop")
          ▼
 private SDK bridge / REST routes
          │ owns lifecycle + loopback endpoints
          ▼
    ComputerSandbox
          │ reuses SmolVM VM, exec, files, networking
          ▼
 published linux-desktop image
          │
          ├── graphical session ──► display.viewerUrl / display.vncUrl
          └── Chromium CDP proxy ─► browser.cdpUrl
```

### One lifecycle implementation

Extract a neutral internal `GraphicalSessionConfig`, `GraphicalSessionInfo`, and `GraphicalSessionLifecycle`. This layer owns VM creation, display startup, endpoint forwarding, readiness, diagnostics, and cleanup. `BrowserSandbox` and the new `ComputerSandbox` are thin adapters that select image, user, applications, and required capabilities. They write one graphical-session record rather than parallel browser and computer records.

The browser API becomes a compatibility adapter over this lifecycle with browser-focused configuration and existing behavior. Do not maintain separate browser and computer implementations that can drift on cleanup or endpoint security.

The image builder may emit two images from shared layers:

- `browser-chromium-*`: current small browser image and browser-session defaults;
- `computer-linux-desktop-*`: browser layer plus desktop applications and desktop autostart configuration.

This keeps existing browser downloads small. Shared scripts and Dockerfile fragments prevent behavior duplication.

### Protocol and capability negotiation

Add runtime capabilities for create, delete, endpoints, exec, files, and events. A computer response includes a capability list so future templates can add features without inferring support from missing URLs.

Initial `linux-desktop` guarantees:

```text
display.viewer
display.vnc
browser.cdp
sandbox.exec
sandbox.files
computer.events
```

The public event payload is:

```ts
type ComputerEvent =
  | { type: "computer.starting"; computerId: string }
  | { type: "computer.ready"; computerId: string; sandboxId: string }
  | { type: "computer.error"; computerId: string; sandboxId: string; process: string; message: string }
  | { type: "computer.stopping"; computerId: string; sandboxId: string }
  | { type: "computer.deleted"; computerId: string; sandboxId: string };
```

Python exposes the equivalent `ComputerEvent` typed-dictionary union with snake_case fields through `on_event`. The bridge translates those identifiers to camelCase for TypeScript. `computer.error` names the failed required process and includes one short recovery message; it moves the owning handle to `error`, rejects new operations, and leaves deletion retryable.

Endpoint URLs remain loopback-only. They may appear only in an explicit create/get response, `computer open`, or requested JSON output. Errors, events, diagnostics, telemetry, and debug logs redact their host, port, and query credentials.

### Private bridge contract

The TypeScript bridge adds only these process-owned routes:

| Method and route | Request | Success |
|---|---|---|
| `POST /computers` | `CreateComputerRequest` | `201 ComputerResponse` after full readiness |
| `DELETE /computers/{computer_id}` | none | `204`, including repeated deletion |
| `POST /computers/{computer_id}/exec` | existing `ExecRequest` | existing `ExecResponse` |
| `GET /computers/{computer_id}/files?path=<absolute>` | none | binary body, existing 16 MiB limit |
| `PUT /computers/{computer_id}/files?path=<absolute>` | binary body | `204`, written atomically as `agent` |
| `POST /computers/{computer_id}/browser/launch` | none | current browser status and CDP URL |
| `GET /sdk/v1/events` | existing SSE request | existing stream carrying the computer event union |

`CreateComputerRequest` has `computer_id?`, `template`, `backend`, `display { width, height }`, `resources { memory_mib, disk_mib, vcpus }`, `network`, and `workspace`. `computer_id` uses the existing identifier validator. `ComputerResponse` has required `computer_id`, `sandbox_id`, `template`, `status: "ready"`, `capabilities`, `display { viewer_url, vnc_url }`, and `browser { status, cdp_url }`. Only `computer_id` targets computer routes; `sandbox_id` is returned for correlation and cannot address them.

The bridge reuses the existing network, workspace, exec, and file-size DTOs rather than defining alternate validators. Computer file writes add the `agent` ownership behavior described below. Generated OpenAPI tests freeze every field, route operation ID, and these mappings:

- `400` with `computer_image_unavailable` or `computer_create_failed` for a valid request that cannot start;
- `404` with `computer_not_found` for a non-existent live SDK computer, except idempotent delete;
- `408` with `command_timeout` when exec times out and cleanup is attempted;
- `409` with `computer_already_exists`, `computer_not_ready`, `transport_failed`, or `cleanup_failed` for the named state;
- `413` with `file_too_large` for the existing file limit;
- `422` with the existing validation response for malformed identifiers, templates, resources, paths, mounts, or policies.

All errors use the existing `ErrorResponse`. It may contain a stable code, concise recovery, and bounded redacted diagnostics, but never endpoint URLs, credentials, or raw guest output. The Python class factory calls the same internal lifecycle directly and mirrors these codes without routing through the bridge.

### Compatibility

- Keep `SmolVM.browsers.create()` and `smolvm browser ...` working.
- Keep existing `BrowserSessionClient` names and event types for existing callers.
- Implement browser creation through the shared graphical lifecycle after parity tests pass.
- Do not silently translate `mode: "desktop"` into the new Linux template. Mark it deprecated only after `computers.create()` ships and documentation has migrated.
- Keep the existing Python `SmolVM.desktop()` behavior unchanged in this release. Document TypeScript `smolvm.computers.create(...)` and Python `SmolVM.computer(...)` as the richer replacements, but do not alias or deprecate `desktop()` until a later major-version decision.

### Lifecycle and observability

V1 does not add a resident system daemon. SDK computers remain owned by the creating Python handle or TypeScript bridge and are deleted when that owner closes. CLI computers use the existing locked SQLite inventory and backend processes that survive the starting command. Later CLI invocations reconnect from that inventory for `list`, `open`, `logs`, or `delete`.

Crash recovery uses a write-ahead ownership journal in the existing SQLite state database. Before any SDK VM, disk, forward, or firewall rule is allocated, the owner transactionally records the computer ID, owner PID plus process-start token, host boot ID, and intended operation. It atomically adds each resource ID before exposing that resource and removes entries only after confirmed cleanup. Endpoint URLs and credentials are never journaled. Every Python factory, TypeScript bridge, and computer CLI startup scans the journal: an entry whose boot ID or owner process token is no longer live is promoted to a CLI-visible `error` record and reconciled before new allocation. This makes abrupt exit discoverable without a resident daemon and avoids PID-reuse mistakes.

Creation writes the CLI inventory record before VM allocation and blocks until every readiness probe succeeds. A returned `ComputerSession` is always `ready`; a failed CLI create leaves an `error` record with diagnostics but no usable endpoints. The SDK reports the same error and completes its owned cleanup without retaining a cross-process record. While an SDK owner is alive, its lightweight health check watches Xvfb, Openbox, x11vnc, and websockify. If one exits after readiness, the owner emits `computer.error`, marks the handle `error`, rejects new work, and retains the computer for explicit retryable deletion. V1 does not silently restart these required processes.

Chromium, the panel, terminal, file manager, and editor are applications rather than the computer's lifecycle. A person may close them without destroying the computer. If Chromium closes, `computer.status` remains `ready`, `computer.browser.status` becomes `closed`, and `cdpUrl` becomes `null`. Calling `computer.browser.launch()` starts or focuses Chromium idempotently and restores CDP. The root-owned supervisor may restart Tint2 after an accidental panel crash, but never reopens a user-closed application without an explicit launch call.

Computer events are `computer.starting`, `computer.ready`, `computer.error`, `computer.stopping`, and `computer.deleted`. Each includes `computerId`; every event after `starting` also includes `sandboxId`. Events are ordered per owner process, best-effort, not replayed, and may omit intermediate states when an observer reconnects. The current handle status or a reconciled CLI `computer list` is authoritative. Observer exceptions never change computer behavior.

Deletion proceeds in a fixed, retryable order:

1. mark the record `stopping` and reject new work;
2. capture the latest root-owned startup and process logs;
3. close CDP, VNC, and noVNC forwards;
4. stop the graphical session and VM;
5. remove its ephemeral disk and runtime state;
6. mark the record `deleted` and remove diagnostics.

If a CLI cleanup step fails, the inventory record becomes `error`, records the unresolved resource identifiers, and keeps mode-`0600` diagnostics under SmolVM's existing local state directory. Repeating `computer delete <id>` reconciles the remaining resources. SDK deletion retries within the live owner and reports any unresolved resource identifiers without placing secrets in the error. A successful repeated delete is a no-op.

`ComputerSession.delete()` keeps its cleanup state and handle registered until every owned resource is reconciled, so a failed call can be repeated. TypeScript `SmolVM.close()` attempts every owned deletion but does not close the transport, clear the active handle, or permanently cache a rejected close promise while any deletion remains unresolved; another `close()` retries. It closes the transport only after cleanup succeeds or after it has persisted an exceptional orphan record for CLI reconciliation. Python context-manager exit follows the same handle rule and raises a cleanup error without discarding the still-retryable handle state.

### Readiness contract

`ready` means all of the following passed within one bounded creation deadline:

- the VM guest agent accepts `exec` and a write/read probe in `/workspace` succeeds;
- Xvfb, D-Bus, Openbox, Tint2, x11vnc, and websockify are running;
- the panel and Chromium each have a mapped window on the requested display at initial readiness;
- the noVNC HTTP endpoint and VNC socket answer through their host forwards;
- Chromium's `/json/version` endpoint answers through the CDP proxy;
- a CDP-created tab appears on the same framebuffer returned by VNC.

A missing panel, unmapped Chromium window, permission mismatch, or partial endpoint set fails creation.

## Security boundaries

- noVNC, VNC, and CDP bind through loopback-only host forwards.
- V1 treats other processes owned by the same host account as trusted because the endpoints have no application password. Remote or multi-user host access requires a future authenticated proxy.
- The image contains no default password and no reusable secret.
- Chromium's debugging port stays on guest loopback behind the existing proxy path.
- PID files, supervisor scripts, and logs remain root-owned.
- The `agent` user cannot modify startup scripts or root-controlled runtime paths.
- The default template is ephemeral. Persistent Chromium login and full desktop persistence are deferred until dedicated versioned artifacts and locking exist.
- Workspace mounts and network access use existing validated SmolVM policies.
- Guest service ports are reachable only through the host-forwarding path. QEMU computer sessions use isolated user-mode networking and explicit host forwards; they do not join a shared guest network. Firecracker gives each computer a dedicated point-to-point TAP subnet and installs host rules that accept its VNC, noVNC, and CDP proxy ports only from that host-side TAP. The guest services may bind their private guest interface so those forwards work, but no two computers share a reachable service network. A backend is not eligible until a negative peer-connectivity test passes.
- A graphical terminal is not a security boundary. Anything controlling the desktop can type commands into it. Applications must not combine untrusted autonomous screen control with host secrets or privileged mounts.

## Failure and rescue registry

| Failure | Detection | Cleanup | User recovery |
|---|---|---|---|
| Image unavailable | verified download error | remove partial image file and retain error record | run `smolvm computer logs <id>`, delete it, then rerun the original start command |
| VM boot timeout | bounded VM readiness deadline | close forwards and stop/delete the owned VM | run `smolvm computer logs <id>`, then `smolvm computer delete <id>` |
| X server missing | display socket and process probe | enter `error` and run retryable cleanup | run `smolvm computer logs <id>`, then `smolvm computer delete <id>` |
| X server, window manager, VNC, or noVNC exits after startup | owner health check and `computer.error` | mark `error` and keep cleanup explicit | run `smolvm computer logs <id>`, delete it, then start another computer |
| Chromium is closed | process probe | keep computer ready and set browser status to `closed` | call `computer.browser.launch()` or open Chromium from the menu |
| Panel crashes | process probe | restart Tint2 once without disturbing applications | open the menu after the panel returns; inspect logs if it fails again |
| VNC/noVNC unavailable | guest-port and host HTTP probes | enter `error` and run retryable cleanup | run `smolvm computer logs <id>`, then `smolvm computer delete <id>` |
| Chromium/CDP unavailable | `/json/version` and framebuffer probes | enter `error` and run retryable cleanup | run `smolvm computer logs <id>`, then `smolvm computer delete <id>` |
| Viewer disconnects | websocket close | keep computer running | reload the same viewer URL |
| TypeScript owner closes cleanly | owner `close()` runs | delete SDK-owned ephemeral computer before closing transport | call `smolvm.computers.create()` again |
| Python handle exits cleanly | context manager exits | delete SDK-owned ephemeral computer | call `SmolVM.computer()` again |
| SDK owner crashes or cleanup stays incomplete | stale ownership journal or bounded retry exhaustion | promote a redacted orphan record to CLI inventory | run `smolvm computer delete <id>` |
| Cleanup only partly succeeds | remaining-resource reconciliation | retain `error` record and diagnostics | rerun `smolvm computer delete <id>` |
| Delete called twice | stored terminal state | no-op | none |

## Success criteria

1. A new developer can create a Linux computer and print all three endpoints in fewer than ten lines of TypeScript.
2. The live view shows Chromium plus a usable panel with cached warm-ready p95 no more than five seconds slower than browser live mode.
3. Terminal, Files, and Text Editor launch from the panel and start in `/workspace`.
4. A Playwright navigation through `computer.browser.cdpUrl` is visible in the same `computer.display.viewerUrl` display.
5. `exec`, files, VNC input, CDP, and human viewing operate on the same VM.
6. Startup never returns a partly ready handle. Failed creation runs bounded cleanup; unresolved CLI resources remain in its inventory, while unresolved SDK resources remain retryable through the live owner or an exceptional orphan record after owner loss.
7. Existing browser-session tests and API contracts continue to pass.
8. The desktop image is built, smoked, published, and pinned through the repository's image release checklist.
9. Its compressed candidate is no more than 250 MiB larger than the browser image produced by the same architecture build.

## Not in scope

- Windows and macOS computer templates. Their future names and capability model are reserved, but no guest work ships now.
- Persistent desktop or browser profiles.
- Audio, camera, GPU acceleration, USB passthrough, printing, and multi-monitor displays.
- VS Code, office suites, full GNOME/KDE/XFCE, or arbitrary user-selected desktop packages.
- A core SmolVM human/agent control broker. OpenMuse continues to own that policy.
- Background desktop-process health events and automatic recovery after readiness.
- Claims that every website permits automation.
