## Problem Statement

Before this work, OpenMuse worked only when its operator created `.env.local` and added an `OPENAI_API_KEY`. That was appropriate for a developer example, but it excluded users who already paid for access through a supported model-provider account and expected a normal sign-in experience.

The desired first run is simple: choose a supported account, finish authentication in the user's normal browser, select a model, and start chatting. API keys remain available under an advanced path. OAuth credentials stay in the trusted host process. An API key typed in the setup page exists transiently in that input and its loopback request, but is never returned to the client, retained in application state after submission, logged, or sent to the disposable VM, agent-controlled browser, diagnostics, or conversation history.

## What Makes This Cool

OpenMuse stops feeling like a source checkout that must be wired to a developer account. A user can clone it, click **Continue with OpenAI**, sign in, and reach the existing chat screen without copying a secret.

The deeper product improvement is that the interface does not hardcode this one provider. It asks Pi which authentication methods each installed provider actually supports. A future Pi release can add account authentication without forcing OpenMuse to invent another login architecture.

## Starting Point

OpenMuse pins `@earendil-works/pi-ai` and `@earendil-works/pi-agent-core` at `0.85.1`. At the start of this work, the server:

- registers only `openaiProvider()`;
- chooses one process-wide `OPENAI_MODEL`;
- passes one process-wide `OPENAI_API_KEY` into every agent; and
- creates or restores a conversation during client bootstrap, before checking whether model access is available.

Pi `0.85.1` already provides the important authentication primitives:

- a `Provider` descriptor with `apiKey` and optional `oauth` capabilities;
- `Models.login()`, `logout()`, `checkAuth()`, `getAvailable()`, and `getAuth()`;
- an app-owned `CredentialStore` abstraction;
- provider-neutral prompts and notifications for browser URLs, device codes, progress, manual codes, selections, and secrets; and
- locked OAuth refresh so concurrent requests cannot rotate the same refresh token twice.

Its built-in account flows include OpenAI Codex, Anthropic, GitHub Copilot, and OpenRouter. The built-in Google provider accepts a Gemini API key. Vertex AI accepts an API key or Application Default Credentials. This version does not expose Gemini CLI personal-account authentication as a Google OAuth capability.

Provider support and account-login support are therefore separate capabilities. OpenMuse must not display **Continue with Google** as an active action until the installed Google provider actually exposes that method.

## Constraints

- Preserve the host-only credential boundary from the existing OpenMuse designs.
- Never open provider authentication inside the agent-controlled VM or its browser profile.
- Keep OpenMuse loopback-only and single-user.
- Use Pi's public provider and authentication contracts rather than importing its private OAuth modules.
- Do not persist access tokens, refresh tokens, API keys, authorization codes, or typed secrets in application events, diagnostics, errors, conversation checkpoints, browser tools, or logs.
- Keep fixture mode and deterministic tests independent of network access and real provider accounts.
- Do not silently switch provider, model, account type, or billing path.
- Show only authentication methods supported by the installed provider descriptor.
- Verify provider terms for embedded open-source use before enabling a subscription-backed flow in a release.

## Premises

1. The user is choosing how OpenMuse may access a model, not configuring Pi internals.
2. Account authentication happens in the user's normal browser. The agent's browser never participates.
3. Pi provider descriptors are the runtime source of truth for available authentication methods.
4. The first account release supports OpenAI Codex through Pi's existing OAuth flow.
5. OpenAI and Gemini API keys remain advanced alternatives.
6. Google account authentication is deferred until a Pi-compatible provider exposes and maintains it.
7. OpenMuse remains a local, single-user application. Hosted callbacks and multi-user tenancy are separate designs.

## Approaches Considered

### Approach A: OpenAI account vertical slice

Add an OpenAI-specific login route and screen around `openai-codex`, while preserving the existing environment-key path. This proves the OAuth callback and gets users to a first conversation quickly, but it creates OpenAI-shaped server and client contracts that must be replaced for the second account provider.

Completeness: 7/10. Estimated effort: human 1–2 days; coding agent 3–5 hours. Risk: medium.

### Approach B: Capability-driven authentication service

Create one host-side authentication service around Pi's `Models`, `Provider`, and `CredentialStore` interfaces. It exposes sanitized provider capabilities to the client, translates Pi's interactive login protocol into a local attempt lifecycle, persists credentials, resolves and refreshes them for requests, and binds each conversation to an explicit provider and model.

Completeness: 10/10. Estimated effort: human 3–5 days; coding agent 1–2 days. Risk: medium.

### Approach C: Pi CLI authentication companion

Ask users to run `npx @earendil-works/pi-ai login` separately, then make OpenMuse reuse the resulting file. This minimizes OpenMuse code but fails the chosen first-run experience and couples recovery to a second interface.

Completeness: 4/10. Estimated effort: human 1 day; coding agent 2–3 hours. Risk: low technically and high for usability.

## Recommended Approach

Use Approach B. Pi already owns provider-specific login, refresh, and request-auth conversion. OpenMuse should own the application concerns around it: storage, safe local transport, visible state, conversation binding, and recovery.

### 1. Model access service

Replace the process-wide `apiKey` and `model` fields in `ConversationManager` with a `ModelAccessService`. It owns one long-lived Pi `Models` collection and registers only providers OpenMuse intentionally supports:

- `openai-codex` for eligible account-backed Codex access;
- `openai` for OpenAI Platform API keys;
- `google` for Gemini API keys in milestone 2, after the account-first slice is proven.

Provider registration is an explicit allowlist, not `providers/all`. Milestone 1 registers only `openai-codex` and the existing `openai` provider. The service keeps generic interfaces, but Gemini API-key registration and Google account login are milestone 2 work. Adding a provider changes what data leaves the machine and what terms apply, so a dependency upgrade must not silently expose it.

The service presents a sanitized description for each provider:

```ts
interface ProviderAccessSummary {
  id: string;
  name: string;
  configured: boolean;
  source?: "account" | "api_key" | "environment";
  methods: Array<{
    type: "oauth" | "api_key";
    label: string;
    enabled: boolean;
    unavailableReason?: string;
  }>;
  models: Array<{ id: string; name: string; recommended: boolean }>;
}

interface ModelAccessSnapshot {
  providers: ProviderAccessSummary[];
  selection?: { providerId: string; modelId: string };
  disconnectingProviderIds: string[];
}
```

`oauth` exists when `provider.auth.oauth` exists. `api_key` is an interactive choice only when `provider.auth.apiKey.login` exists. Environment variables and Application Default Credentials are resolution sources inside Pi's `apiKey` capability, not login methods; when `checkAuth()` detects one, the summary reports configured status without offering it as a selectable method.

No summary contains an email address, account ID, token fragment, key prefix, filesystem path, or raw Pi source label. OpenMuse can add a non-secret account label later only after a separate privacy decision.

### 2. Credential store

Implement all four Pi `CredentialStore` methods in `open-muse/server/credential-store.ts`: `read`, `list`, `modify`, and `delete`. Every method honors an already-aborted signal before filesystem work. `modify` serializes each provider's complete read-modify-write sequence; `list` returns provider ID and credential type only and never resolves commands or refreshes credentials.

- Store credentials at `.open-muse/auth.json` by default; allow `OPEN_MUSE_AUTH_PATH` for tests and advanced local use.
- Create the parent directory with mode `0700` and the file with mode `0600`.
- On macOS and Linux, verify ownership and permissions on load and before every successful write. Repair overly broad modes with `chmod` only when the current user owns the path; reject a path owned by another user. Windows reports that owner-only filesystem enforcement is unavailable rather than claiming the POSIX guarantee.
- Use a versioned document `{ fileVersion: 1, credentials: Record<string, Credential> }`, capped at 1 MiB and 100 provider entries. Validate the type tag and required base fields while preserving unknown provider-specific OAuth fields.
- Refuse a symlink destination to prevent accidental redirection. OpenMuse does not claim protection from a malicious process running as the same OS user.
- Serialize mutation with a process-wide queue. Acquire an adjacent lock using exclusive creation, retry for at most five seconds, and store the PID plus creation time. On macOS and Linux, replace a lock older than 30 seconds only when its PID no longer exists. If a PID was reused and appears alive, fail after five seconds with the exact lock path and a command to inspect or remove it; never wait indefinitely or delete a possibly live lock. On Windows, fail with the exact lock path instead of guessing whether a lock is stale.
- Write a complete new document to a same-directory temporary file, sync it, set permissions, and atomically rename it.
- Sync the containing directory after rename on macOS and Linux, matching `ConversationStateStore`; document the weaker Windows crash-durability guarantee.
- Validate the complete document before use. Unknown provider records remain untouched so downgrades do not destroy credentials.
- Never include the credential file in conversation checkpoints or diagnostic bundles.
- Logout deletes the provider entry and atomically rewrites the file. When no entries remain, retain an empty owner-only file so permissions stay deterministic.

The first release uses this portable owner-only file because that matches Pi's storage contract and OpenMuse's source-checkout distribution. Extract and reuse the atomic JSON-write helper from `ConversationStateStore` rather than creating a second durability implementation. Native keychain storage is a later hardening option, not a prerequisite hidden inside this scope.

### 3. Authentication attempt lifecycle

OAuth and device login are longer-lived than one HTTP request. Represent each login as a short-lived in-memory attempt:

```ts
type AuthAttemptState =
  | "starting"
  | "waiting_for_browser"
  | "waiting_for_device"
  | "waiting_for_input"
  | "succeeded"
  | "expired"
  | "cancelled"
  | "failed";
```

Each attempt has a random 256-bit identifier, provider ID, chosen method, creation time, deadline, current prompt metadata, abort controller, and sanitized events. It never contains serializable credentials. The deadline follows a provider `expiresInSeconds` event when supplied, capped at 20 minutes; otherwise it is five minutes.

Only one attempt may run per provider. A second request returns: **Sign-in is already open for OpenAI. Finish it, or cancel it before trying again.** Each attempt belongs to the authenticated local session that created it. Attempts are cancelled when the user cancels, when their session expires, when the deadline expires, or when OpenMuse shuts down. A page refresh may resume an attempt because bootstrap reuses the valid cookie and `sessionStorage` retains its unguessable attempt ID; an SSE disconnect alone never cancels it.

Pi's `AuthInteraction` maps as follows:

- `auth_url`: send the exact HTTPS URL to the trusted client, which opens it in a new tab in the user's normal browser;
- `device_code`: display the verification URL and user code, with a copy action for the code;
- `select`: display Pi's supplied choices, including OpenAI's browser-login versus device-code choice before either flow begins;
- `manual_code`: accept one authorization code or callback URL in a secret-like field that is never retained;
- `secret`: accept an API key through the same protected local channel; and
- `progress` or `info`: show bounded provider text after stripping URLs except separately typed links.

The OpenAI browser callback is received by Pi's loopback listener in the trusted host process. The OpenMuse UI must explain that the new browser tab is provider-controlled and that the agent's VM is not involved. Pi does not expose a typed callback-port failure: its browser flow falls back to a `manual_code` prompt. OpenMuse must not string-match that failure or claim automatic device-code fallback; users choose device code in Pi's initial selection if they expect the callback to be unreachable.

On success, `Models.login()` persists through the injected credential store before the attempt becomes `succeeded`. A failed persistence leaves the provider unconfigured and reports: **OpenAI sign-in finished, but OpenMuse could not save it. Check permissions for `.open-muse/auth.json`, then try again.**

Auth attempt events use monotonically increasing IDs and the existing SSE replay convention. Keep at most 100 events per attempt. `Last-Event-ID` replays retained events; a gap returns `auth.resync_required` and closes the stream so the client fetches the attempt snapshot. Each prompt has a random ID, one accepted response, and the attempt deadline. A duplicate or stale prompt response returns `409`; an unknown or expired attempt returns `404` with a restart action. Terminal snapshots remain readable for 60 seconds and are then removed; reading them does not consume them.

### 4. Local API

Extend the existing loopback session and CSRF protection. New routes use the same authenticated cookie; every mutation requires `x-smol-csrf`. Refactor `server/index.ts` so `assertMutation()` runs for every method except `GET`, `HEAD`, and `OPTIONS`; the current POST-only check is insufficient for these PUT and DELETE routes.

```text
GET    /api/model-access
POST   /api/auth-attempts
GET    /api/auth-attempts/:attemptId
GET    /api/auth-attempts/:attemptId/events
POST   /api/auth-attempts/:attemptId/prompts/:promptId
DELETE /api/auth-attempts/:attemptId
DELETE /api/model-access/providers/:providerId
PUT    /api/model-access/selection
```

`POST /api/auth-attempts` returns `{ attempt: AuthAttemptSnapshot }`; attempt GET and SSE events use that same redacted snapshot shape. A prompt submission accepts `{ value: string }` and returns the next snapshot. Selection returns `{ providerId, modelId }`. Cancellation and logout return `{ stopping: true }`; cancellation is confirmed through the attempt snapshot or SSE stream, while logout is confirmed through `GET /api/model-access`. Snapshots expose prompt labels and choices but never the user's submitted value.

Authentication-attempt cancellation is observed on the attempt snapshot and SSE stream. Provider logout is observed on `GET /api/model-access`; these are separate `202` lifecycles.

`POST /api/auth-attempts` accepts `{ providerId, method }`. `PUT /api/model-access/selection` accepts `{ providerId, modelId }` after `checkAuth()` and the known catalog confirm that the provider is configured and the model exists. Immediately before a model request, `getAuth()` proves request-valid access and performs any required refresh; `getAvailable()` alone does not prove that an expired OAuth token can refresh.

All JSON bodies and responses have strict Zod schemas and a 32 KiB request-body limit. Provider and model IDs are capped at 80 and 200 characters. Provider-generated labels, messages, and instructions are capped at 500 characters; an attempt exposes at most 20 choices with 80-character IDs and 200-character labels. Links are HTTPS and capped at 2,048 characters. Secret values are capped at 16 KiB, manual callback/code values at 8 KiB, and text/select responses at 1 KiB. Successful create returns `201`, prompt submission and selection return `200`, and cancellation/logout return `202` while settlement is pending. Use `400` for invalid bodies, `404` for unknown or expired resources, `409` for duplicate attempts, stale prompts, unavailable models, or logout already in progress, and `503` when provider access cannot currently be resolved. Every error payload is `{ error: string, code: string }` with no nested cause.

API-key setup also uses an attempt and a Pi `secret` prompt. The raw key exists only in trusted-host handling: the transient browser input and loopback request, Pi interaction, credential file and reads, Pi auth resolution, and the outbound provider request. It is never returned to the browser after submission. Request-body parsing, error handling, tracing, tests, and diagnostics must never echo it.

All route identifiers are allowlisted and length-bounded. Random, unguessable attempt IDs plus loopback session authentication protect attempt lookups; terminal attempts are removed after their 60-second retention window.

All provider exceptions cross one named `sanitizeModelAccessError(error)` boundary before reaching HTTP, SSE, diagnostics, console logging, or persisted state. It maps known application conditions by code, collapses untyped provider denial, network, and callback failures into a generic `auth_failed`, strips URLs and query strings, and never serializes `cause` or a provider response body.

### 5. Bootstrap and client flow

`GET /api/bootstrap` returns the CSRF token, resumable conversation ID if one exists, and the `ModelAccessSnapshot`. It no longer creates a conversation indirectly.

Replace `Map<sessionCapability, csrfToken>` with a bounded `LocalSession` record containing the CSRF token, pending provider/model selection, creation time, last-seen time, and owned auth-attempt IDs. Bootstrap reuses a valid cookie instead of issuing a new session on every refresh. Sessions expire after 12 hours idle or 24 hours absolute, are capped at 32 most-recently-used entries, and are cleaned during bootstrap plus a 15-minute timer. Replacing or expiring a session cancels its attempts and clears its pending selection; it does not delete configured provider credentials or conversations.

The selected provider/model is stored in this server-side local session until conversation creation. Creating a conversation copies both identifiers into durable conversation state. Changing the pending preference affects only future conversations; continuing a restored conversation uses its own binding unless the user explicitly confirms a switch.

Client startup follows these states:

1. **No configured provider:** show the account chooser instead of creating a conversation.
2. **Signing in:** show the browser, device-code, prompt, cancellation, and failure states from the active attempt.
3. **Provider configured, no valid selection:** show available models and require an explicit choice. A curated recommendation may be preselected but remains visible before conversation creation.
4. **Provider and model selected:** create or restore a compatible conversation and enter the existing chat UI.
5. **Restored conversation lacks access:** preserve its messages, show **Reconnect OpenAI to continue this conversation**, and do not create a new VM or run the model.

The advanced section offers OpenAI and Gemini API keys only when those providers are registered. Environment-provided keys appear as **Configured from your environment** and cannot be revealed or deleted through OpenMuse; the UI names the exact environment variable to remove outside the app.

### 6. Conversation binding

Advance `state.json` to `fileVersion: 3` and persist `providerId`, `modelId`, and a separate `modelAccessState: "ready" | "auth_required" | "model_unavailable"` with every conversation. Do not add authentication conditions to `RunState`; browser/tool execution state and model-access state are independent.

Migrate file versions 1 and 2 by assigning the configured legacy OpenAI provider plus `OPENAI_MODEL` when that model still exists. If no matching provider or model is configured, preserve messages and operation history and set `modelAccessState` to `auth_required` or `model_unavailable`. Unknown provider IDs are preserved in the stored record for recovery but are never instantiated. A restored conversation must use the same provider unless the user explicitly chooses **Switch model provider**. To switch, block new turns, abort and settle any active agent, validate the new provider/model with `getAuth()`, construct a new `Agent` with the existing public message transcript and browser tools, then checkpoint the new binding before accepting another turn. If validation, construction, or checkpointing fails, retain the old binding and agent. Cross-provider continuation is technically possible in Pi, but changing provider affects billing, retention, model behavior, and available context. It is never an automatic recovery.

Construct `Agent` with `streamFn: models.streamSimple.bind(models)` and omit `getApiKey`, preserving provider-specific keys, headers, and base URLs. Immediately before `Agent.prompt()` or `continue()`, call `models.getAuth(model)` as a typed preflight. If it throws `ModelsError` with code `oauth`, set `modelAccessState` to `auth_required` without starting the agent turn. The subsequent stream performs its normal request-time resolution, causing two credential reads but at most one refresh because a successful preflight persists the refreshed credential under the store lock. The request-specific token remains in the trusted Node process.

If refresh fails, the current turn ends with a sanitized `auth_required` state. The conversation and VM remain intact but the agent is paused. The UI offers **Reconnect OpenAI** and retries only after successful sign-in and a new user action; it never replays a failed model request automatically.

### 7. Logout and account switching

Disconnecting a provider is explicit and local:

1. block new turns for conversations bound to that provider;
2. call `agent.abort()` for active model streams and await `agent.waitForIdle()` for at most ten seconds;
3. mark affected conversations `auth_required` without deleting messages or VMs;
4. call `Models.logout(providerId)`; and
5. refresh the model-access summary.

If settlement exceeds ten seconds, keep the provider blocked in memory, leave the credential stored, and report that disconnect did not finish; never delete credentials while an unconfirmed stream may still be using them. The UI says **Disconnected from OpenAI on this computer. Your provider account was not deleted.** only after deletion succeeds. If deletion from the local store fails, keep the provider blocked in memory and show the exact local recovery path without claiming success.

Switching accounts performs this logout sequence before starting a fresh login. OpenMuse does not merge credentials or support two simultaneous accounts for the same provider in this milestone because Pi's store contract is one credential per provider.

### 8. Security and privacy invariants

- Credential values are accepted only by the authentication service and credential store.
- The React client may receive a one-time authorization URL or device code, but never an access token, refresh token, API key, or callback authorization code after submission.
- Authentication events use a separate bounded buffer from conversation events and are never persisted.
- Provider errors are mapped to short application errors. Raw response bodies and OAuth query strings are discarded.
- `GET /api/model-access` is metadata-only and safe for repeated polling.
- The noVNC viewer and browser broker cannot access the credential path.
- Fixture mode uses a fake provider and in-memory credential store.
- Validate every provider auth link as HTTPS, then open it with `window.open(url, "_blank", "noopener,noreferrer")`. CSP `frame-src` and `frame-ancestors` prevent provider pages from being embedded in OpenMuse and prevent OpenMuse from being embedded elsewhere; CSP is not treated as a control over top-level navigation.
- Dependency upgrades run a contract test that snapshots the allowlisted providers and authentication capabilities. A new Pi capability cannot become user-visible by accident.

### 9. Terms and provider labeling

Account login and API billing are different products and must be labeled differently:

- **Continue with OpenAI** → eligible ChatGPT account through Pi's `openai-codex` provider;
- **OpenAI API key** → OpenAI Platform usage and billing;
- **Gemini API key** in milestone 2 → Google AI Studio usage and limits.

Before release, maintainers record links to the current provider terms and confirm that the embedded flow is permitted for an open-source local application. Until then, subscription authentication is hidden unless the operator sets `OPEN_MUSE_ENABLE_SUBSCRIPTION_AUTH=1`; the default is off, `.env.example` labels it development-only, and CI asserts that the unset default returns no enabled subscription method. Once approval is recorded in this design or a superseding decision, remove the temporary flag rather than retaining a permanent shadow configuration.

## Failure Matrix

| Condition | User-visible recovery | System behavior |
|---|---|---|
| No provider configured | Choose an account or expand **Use an API key instead** | No conversation or VM starts |
| User explicitly cancels in OpenMuse | **OpenAI sign-in was cancelled. Try again when you're ready.** | Attempt aborts; nothing is stored |
| Provider rejects or cannot complete authentication | **OpenAI sign-in did not finish. Try again, or choose another sign-in method.** | Untyped provider error becomes `auth_failed`; nothing is stored |
| Login expires | **OpenAI sign-in expired. Start sign-in again.** | Attempt and prompts are removed |
| Browser callback unavailable | **OpenAI could not receive the browser result. Paste the final redirect URL here, or cancel and choose device-code sign-in.** | Pi presents its `manual_code` fallback; OpenMuse does not infer the cause |
| Credential write fails | **OpenMuse could not save the sign-in. Check `.open-muse/auth.json`, then try again.** | Provider remains unconfigured |
| OAuth refresh fails | **OpenAI needs you to sign in again. Reconnect it to continue this conversation.** | Turn stops; conversation is `auth_required` |
| Configured model disappears | **This model is no longer available. Choose another OpenAI model to continue.** | No silent model fallback |
| Environment key disappears | **`OPENAI_API_KEY` is no longer available. Restore it, or choose another sign-in method.** | Existing conversation is preserved |
| Logout races with a turn | **Disconnecting after the current model request stops…** | Abort stream, settle, then delete credential |
| Corrupt credential file | **OpenMuse could not read `.open-muse/auth.json`. Restore or remove that file, then restart OpenMuse.** | Do not overwrite the file |

## Testing Strategy

### Unit tests

- credential-store ownership and permission repair, atomic writes, lock serialization, stale-lock recovery, live and reused PID recovery, 1 MiB and 100-entry limits, directory-sync failure, corrupt input, unknown-record preservation, symlink rejection, and logout;
- provider capability projection with tokens and account metadata proven absent;
- login prompt/event translation for every Pi interaction type;
- attempt timeout, cancel, duplicate login, SSE replay gap, terminal retention, stale prompt response, session expiry, and shutdown;
- cross-session isolation for attempt reads, prompt submissions, cancellation, and SSE even when another session knows the attempt ID;
- pending selection survival across bootstrap refresh, exactly-once copy into conversation state, and clearing on session expiry or eviction;
- model selection validation and removal of unavailable models;
- refresh failure mapping and absence of credential material in errors; and
- logout ordering and ten-second timeout against active and queued model turns.

### Server integration tests

- unauthenticated requests cannot read or mutate model access, and missing-CSRF POST, PUT, and DELETE requests all fail;
- bootstrap returns authentication state without creating a conversation or VM;
- fake OAuth success persists before reporting success;
- fake OAuth failure, explicit cancellation, timeout, callback failure, and persistence failure remain recoverable;
- API-key request bodies never enter events, diagnostics, console output, or checkpoints;
- file-version 1 and 2 conversations migrate to a valid binding or an explicit unavailable state;
- restored conversations enter `auth_required` when their provider is unavailable;
- bootstrap reuses valid sessions, expires idle/absolute sessions, and enforces the 32-entry bound;
- the unset subscription-auth release flag fails closed; and
- explicit provider switching preserves messages but never reuses an approval or automatically sends a model request.

### Client tests

- first-run chooser, advanced API-key disclosure, disabled unsupported method, browser handoff, device code, success, and every failure state;
- external auth links open in the user's browser, never the noVNC frame;
- a conversation is not created before access and selection are valid;
- refresh failure returns to reconnect without losing messages; and
- environment credentials are described but never revealable or deletable.

### Live smoke

Keep live authentication outside pull-request CI. A release owner runs opt-in smoke tests with disposable test accounts for each enabled account flow and confirms login, one model turn, refresh or forced expiry, logout, and redacted logs. No credential artifact is uploaded.

## Success Criteria

1. A fresh user can choose **Continue with OpenAI**, complete browser or device-code login, select an available Codex model, and send a first message without creating an API key.
2. `OPENAI_API_KEY` remains a supported advanced path and existing source-checkout setup continues to work.
3. The service and client contracts can add Gemini API-key support in milestone 2 without adding provider-specific routes or UI state.
4. The UI never enables **Continue with Google** unless the installed provider exposes account authentication.
5. OAuth tokens are absent from the client and VM. Typed API keys exist only transiently in an uncontrolled input and loopback request and are absent from retained client state, responses, the VM, conversation state, persisted events, diagnostics, test snapshots, and logs.
6. Expired credentials refresh through Pi's locked flow. Refresh failure pauses the conversation and produces an actionable reconnect path.
7. Logout aborts affected turns, removes the local credential, and preserves conversation messages.
8. All deterministic OpenMuse checks pass without a real account or network request.
9. A dependency contract test fails when the allowlisted provider capability surface changes unexpectedly.
10. With `OPEN_MUSE_ENABLE_SUBSCRIPTION_AUTH` unset, subscription methods are unavailable until maintainers document current terms approval; the development-only opt-in is covered by CI.

## Distribution Plan

OpenMuse remains part of the SmolVM source checkout and uses its existing `npm install` and `npm run dev` path. While the terms gate remains, `open-muse/README.md` keeps API-key setup as the primary supported path and documents account sign-in as a development-only smoke. After approval removes the flag, reorder the README so account sign-in is primary and API keys are advanced.

The existing OpenMuse GitHub Actions workflow runs type checking, unit tests, deterministic evaluations, client build, and browser tests. Add credential-redaction and provider-capability contract tests there. Live provider login stays in a manual release workflow that stores no auth artifacts.

## Dependencies

- Pinned `@earendil-works/pi-ai@0.85.1` public `Models`, `Provider`, and `CredentialStore` contracts.
- Confirmation that Pi's OpenAI Codex flow may be embedded in this open-source local application.
- A browser capable of opening the provider URL and reaching Pi's loopback callback, or device-code fallback.
- Existing OpenMuse loopback session, CSRF, SSE, conversation recovery, and host/VM credential isolation.

Google account login is not a dependency for the first release. It becomes eligible when Pi exposes a supported Google account provider with the same login, refresh, and request-auth contract.
